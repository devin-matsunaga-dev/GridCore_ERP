# DECISIONS.md — Utility ERP

> One line per settled choice. Appended by Claude each session; not relitigated without a WP.

- Bootstrap: modular monolith (ASP.NET Core + Aspire), schema-per-module, events for cross-module effects
- Bootstrap: no Python — this project has no polling/monitoring need (unlike ITMS)
- Bootstrap: external systems simulated behind provider interfaces (IMeterReadingProvider, IPaymentProvider, IVendorProvider, ICrewProvider) from day one
- Bootstrap: Finance is downstream-only — consumes events, posts balanced journal entries, never calls back
- Bootstrap: money is decimal; ledger append-only; corrections are new entries
- Bootstrap: TEST SPEED is a first-class requirement — fast unit pyramid, shared Testcontainer+Respawn for integration, parallel, never --maxcpucount:1 (fixes ITMS slowness)
- Bootstrap: UI = Tailwind + shadcn + lucide per DESIGN.md reference dashboard
- WP-0.1: assembly/namespace prefix is `GridCore` (`GridCore.Modules.<Name>`, `GridCore.Platform`, …); solution file is `GridCore.slnx` (.NET 10 XML format)
- WP-0.1: central package management (`Directory.Packages.props`) + shared `Directory.Build.props` — one place for net10.0, nullable, warnings-as-errors and the xUnit stack; test projects are identified by an `*Tests` name suffix because `IsTestProject` is set too late for a props-file condition
- WP-0.1: modules compose via a `Platform.Modules.IModule` seam (`Name`/`AddServices`/`MapEndpoints`), listed explicitly in `Web.Host/Program.cs` rather than assembly-scanned
- WP-0.1: Aspire `ServiceDefaults` project added alongside `AppHost` (standard Aspire pair; consumed by Web.Host from WP-0.2)
- WP-0.1: fast loop runs `tests/UnitTests.slnf` — `dotnet test` accepts only one project/solution argument, so the documented `tests/*UnitTests` glob was corrected in CONVENTIONS.md
- WP-0.1: no assertion library beyond xUnit's `Assert` (FluentAssertions deliberately not added — 8.x is commercially licensed)
- WP-0.2: `aspire.config.json` lives at the repository root (pointing at `src/AppHost`) so `aspire run` resolves the AppHost from anywhere in a fresh clone
- WP-0.2: AppHost composition lives in `InfrastructureComposition`/`WebComposition` extension methods rather than inline in `AppHost.cs`, so the application model is unit-testable in the fast tier without Docker (`tests/AppHost.UnitTests`)
- WP-0.2: MinIO is composed as a pinned plain `AddContainer` (`minio/minio:RELEASE.2025-09-07T16-13-09Z`) — there is no first-party Aspire integration and the community-toolkit package ships pre-release only; never `latest`, which would change the object store under a demo
- WP-0.2: Keycloak uses the official `Aspire.Hosting.Keycloak` 13.5.2-preview — preview is the only channel Microsoft ships it on; its version tracks the rest of Aspire
- WP-0.2: `AddNpmApp` no longer exists in Aspire 13 (`Aspire.Hosting.NodeJs` → `Aspire.Hosting.JavaScript`); the WP-0.2 spec's "web dev server via AddNpmApp" is implemented as `AddViteApp(...).WithNpm()`
- WP-0.2: the React dev-server resource is skipped when `web/` is absent, so `aspire run` stays green until WP-0.6 creates it
- WP-0.2: infra credentials come from named `Parameters:` in `src/AppHost/appsettings.Development.json` (checked in, dev-only) because Postgres/RabbitMQ/Keycloak/MinIO persist their users into their data volumes — a per-run generated password would lock the AppHost out of the volume it created last run. Production supplies the same parameter names from the environment; Redis keeps Aspire's generated password since no user is persisted in its volume
- WP-0.2: `/health` aggregation comes from the Aspire client integrations registered in `Web.Host` (Aspire.Npgsql, Aspire.StackExchange.Redis, Aspire.RabbitMQ.Client); consequence — `Web.Host` no longer starts standalone, it requires the AppHost-supplied connection strings
- WP-0.3: authentication is plain `AddJwtBearer` bound to an `Authentication:*` section (Authority/Audience/RequireHttpsMetadata/RolesClaimPath/NameClaimType), NOT the Keycloak-specific Aspire client integration — swapping OIDC provider is then a configuration change with no code change, as the WP requires
- WP-0.3: endpoints are gated on **permissions**, never on role names; `RolePermissionMap` is the single place roles become permissions, so re-cutting a role touches one file. `Permissions.All` is discovered by reflection over the constants so a new permission can never be missing from the Administrator grant
- WP-0.3: permission policies are built on demand by `PermissionPolicyProvider` for any `perm:<permission>` policy name (`.RequirePermission(Permissions.Billing.Adjust)`), rather than registering a named policy per permission at startup
- WP-0.3: the host is **secure by default** — a fallback policy requires an authenticated caller, so a new module endpoint cannot ship accidentally public; `/health` and `/alive` in ServiceDefaults opt out with `AllowAnonymous` because Aspire's probes carry no token
- WP-0.3: role claims are normalised to `ClaimTypes.Role` by `GridCoreClaimsTransformation` reading a configured dotted path (`realm_access.roles` for Keycloak, a flat `roles` claim for other providers); an unreadable claim yields no roles rather than an exception, so a token GridCore cannot parse means no access, never a 500
- WP-0.3: roles the realm does not define are ignored rather than rejected — the IdP may carry roles for other systems (`offline_access`, `default-roles-*`) and an unknown role must never widen access
- WP-0.3: the Keycloak realm is checked in as `src/AppHost/keycloak/realms/gridcore-realm.json` and imported **in Development only**, because it carries eight test users with a well-known password; a production realm (same roles and clients, real users) is WP-5.1's to supply
- WP-0.3: `gridcore-web` is a public PKCE client whose audience mapper targets `gridcore-api`; direct access grants stay enabled in the dev realm so the RBAC checks can fetch a token with curl
- WP-0.3: `Web.Host` registers `AddProblemDetails()` + `UseStatusCodePages()` so the framework's own 401/403 carry RFC 7807 bodies, per CONVENTIONS.md
- WP-0.4: EF Core 10 + Npgsql lands here (the first WP that persists anything); `Platform` owns the `platform` schema through `PlatformDbContext`, registered as a plain `AddDbContext`/`UseNpgsql` rather than an Aspire client integration — Platform is a library and must not depend on Aspire; `/health`'s Postgres check stays WP-0.2's `AddNpgsqlDataSource`
- WP-0.4: tables and columns are named explicitly in `IEntityTypeConfiguration` classes rather than adding `EFCore.NamingConventions` — snake_case per CONVENTIONS.md with one fewer dependency; primary keys and indexes are named too (`pk_`/`ix_`) so migrations read the same as the database
- WP-0.4: JSON snapshots are `jsonb` on Postgres; `PlatformDbContext.OnModelCreating` relaxes that column type for non-Npgsql providers so the fast tier runs the *same* model on SQLite in-memory (CONVENTIONS.md rule C) instead of a second model or a container
- WP-0.4: queries order by the Guid v7 primary key, not by the timestamp column — v7 ids sort chronologically as `uuid` on Postgres and as TEXT on SQLite, it reuses the PK index, and SQLite cannot `ORDER BY` a `DateTimeOffset` at all
- WP-0.4: audit snapshots serialise enums by name (`JsonStringEnumConverter`); an entry read years later must not depend on today's enum numbering. The `status` column is stored by name for the same reason
- WP-0.4: `IAuditLog` has two one-liners — `Record` enlists the entry in the current platform unit of work so it commits in the same transaction as the change it describes, `RecordAsync` also saves for writes with no shared unit of work. Cross-context atomicity (a module's DbContext + the platform's) is WP-0.5's to settle alongside the outbox
- WP-0.4: the audit trail is append-only in code — `PlatformDbContext.SaveChanges(Async)` throws if an `AuditEntry` is Modified or Deleted, the same rule the ledger will follow
- WP-0.4: `ICurrentUser` (with `HttpContextCurrentUser` and `SystemUser`) is the seam for "who is acting"; audit and services take it instead of `IHttpContextAccessor` or raw claims. Outside a request the actor is `system` (and is not user-gated, since background work is the host's own); an anonymous caller *inside* a request holds nothing
- WP-0.4: the approval primitive carries its own `RequiredPermission`, checked in `ApprovalService` rather than at the edge — `platform.approve` gets a caller into the queue, the request's own permission decides whether they may decide *that* one, so a PO and a bill adjustment share one table and one workflow
- WP-0.4: separation of duties is enforced in the aggregate — a request may not be decided by whoever raised it, and only the requester may withdraw it; decisions are final (a re-decision means a new request), matching the append-only ledger rule
- WP-0.4: the scheduler is a plain `BackgroundService` over an `IScheduledJob` seam (per-job loop, per-run DI scope, `TimeProvider` for the delay, failures logged and survived) — no Quartz/Hangfire, which the MVP does not need
- WP-0.4: the notification stub is `INotificationSender` + `LoggingNotificationSender`, swapped by DI exactly like the provider interfaces
- WP-0.4: migrations are applied at startup by `PlatformDatabaseInitializer` in Development only (overridable with `Platform:ApplyMigrationsAtStartup`); a production deploy migrates as its own step — WP-5.1's
- WP-0.4: FluentValidation is still not referenced — WP-0.4's edge validation is the aggregate's own guards surfaced as ProblemDetails. The FluentValidation pattern CONVENTIONS.md prescribes lands with the first real CRUD slice (WP-1.1), which is where a validator registration convention belongs
- WP-0.4: `.editorconfig` exempts `**/Data/Migrations/*.cs` from code style — EF writes those files (block namespaces) and they are append-only, never hand-edited
- WP-0.5: MassTransit is pinned to **8.5.10**, the last Apache-2.0 line — 9.x moved to a commercial licence (its nuspec points at massient.com/license instead of carrying an SPDX expression). 8.5.10 ships a first-class `net10.0` target, so nothing is given up. **Never bump to 9.x**; the pin and the reason live in `Directory.Packages.props`
- WP-0.5: MassTransit's **EF transactional outbox** is used rather than a hand-rolled one, and it lives in `PlatformDbContext` (the `platform` schema) so every module publishes into one outbox; `UseBusOutbox()` means `IPublishEndpoint` writes a row instead of reaching the broker
- WP-0.5: the outbox/inbox tables are renamed to snake_case (`inbox_state`, `outbox_message`, `outbox_state`) but their **columns keep MassTransit's PascalCase names** — the library queries its own model, so renaming columns buys nothing and adds a migration to get wrong
- WP-0.5: modules never see MassTransit. Publishing is `IEventPublisher.PublishAsync`; consuming is deriving `IdempotentConsumer<TEvent>`. Swapping transport is a Platform change, and the consume path is testable without a bus
- WP-0.5: **cross-context atomicity** (owed by WP-0.4) is solved with a per-scope shared `DbConnection` (`GridCoreDbConnection`) plus `IUnitOfWork.ExecuteAsync`. Contexts register with `AddGridCoreDbContext<T>`, which also enlists them as `UnitOfWorkParticipant`s; the unit of work attaches every participant to one transaction *before* the delegate runs, saves them all, then commits. A module write, its audit entry and its outbox row are therefore one transaction across three schemas
- WP-0.5: participants are resolved lazily (only when a transaction actually starts) but **all** of them are attached, not just the ones already touched — a context first used inside the delegate would otherwise silently open its own transaction
- WP-0.5: consumer idempotency is GridCore's own `IMessageDeduplicator` over `platform.processed_messages`, keyed on (message, consumer) so several modules may each react once to the same event. MassTransit's inbox filter is deliberately not enabled — one dedupe mechanism, and it is the one ARCHITECTURE.md names
- WP-0.5: the dedupe read-then-insert takes no lock. Two racing deliveries both insert, the composite PK rejects the loser, its transaction rolls back and the broker redelivers it — one wasted redelivery beats a lock on every message
- WP-0.5: the claim is written in the same transaction as the consumer's work, so a consumer that throws leaves no claim behind and the redelivery genuinely retries instead of being skipped as done
- WP-0.5: `IdempotentEventHandler` (unit of work + dedupe + run) is free of MassTransit types, and `IdempotentConsumer<TEvent>` is a three-line adapter over it — that is what puts the whole consume path in the fast tier
- WP-0.5: events are positional records with a static `For(...)` factory that stamps `Guid.CreateVersion7(occurredAt)`, matching `AuditEntry.For`/`ApprovalRequest.Raise`. The publisher refuses an event with an empty `EventId`, because a message no consumer can deduplicate is a double posting waiting to happen
- WP-0.5: Finance's seam is `IJournalPostingSeam` with a `LoggingJournalPostingSeam` no-op, swapped by DI exactly like the notification stub. The mapping to double entry (`FinancePostings`) is pure and **already balanced-or-throw** (`JournalPostingIntent.For`), so invariant 3 is enforced from today even though the ledger itself is WP-2.6's
- WP-0.5: `FinanceAccounts` holds placeholder account codes (1000/1100/1300/2000/4000) until WP-0.8 ships the chart of accounts by migration and WP-2.6 looks codes up against it
- WP-0.5: `AddGridCoreMessaging` is called **after** `AddModules` in `Program.cs` and reads the consumers back off the `IServiceCollection` (the `AddScheduledJob` trick) — the bus composition stays explicit, nothing is assembly-scanned
- WP-0.5: a missing `rabbitmq` connection string throws a named `InvalidOperationException` at startup, matching the platform schema's behaviour — a host that boots without a broker would accept writes and silently never deliver their events
- WP-0.5: `tests/Contracts.UnitTests` added (first project to test `Contracts`), registered in both `GridCore.slnx` and `tests/UnitTests.slnf`
- WP-0.5: the gate-tier `OutboxFixture` starts **one** Postgres and **one** RabbitMQ container for the whole messaging collection and applies migrations once, per CONVENTIONS.md rule D. It is deliberately minimal — WP-0.7 owns generalising it (and adding Respawn) for the rest of the gate suite

- WP-0.6: the SPA is Vite + React 19 + TypeScript in `web/`, hosted by the AppHost's existing `AddViteApp` resource; the dev server is served **unproxied on a fixed 5173** (`WebComposition.WebAppPort` + `strictPort` in `vite.config.ts`) because the Keycloak realm registers `gridcore-web` at `http://localhost:5173` — a drifting port is a rejected `redirect_uri`, not a warning
- WP-0.6: Aspire's **default proxied endpoint is wrong for an OIDC SPA** — it fronts the dev server on a randomly allocated port, so the browser's origin (and therefore its `redirect_uri`) changes every run and Keycloak refuses the login. `WithGridCoreWebAppEndpoint` sets `Port`/`TargetPort` and `IsProxied = false`; unit tests assert the AppHost port, the realm export's registered URIs and `vite.config.ts` all agree, because the failure only shows up at login time
- WP-0.6: OIDC in the browser is `react-oidc-context` + `oidc-client-ts` (Authorization Code + PKCE against the public `gridcore-web` client). Tokens live in **sessionStorage**, not localStorage, so closing the tab ends the session
- WP-0.6: the AppHost hands the SPA `VITE_OIDC_AUTHORITY/CLIENT_ID/AUDIENCE` (`WithGridCoreWebAppConfiguration`), built from the *same* `ReferenceExpression` as the API's `Authentication__Authority` — a unit test asserts the two are equal, because a different host for login than for validation fails issuer matching silently
- WP-0.6: the browser reaches the API same-origin through Vite's `/api` proxy, whose target comes from Aspire's `services__web-host__<scheme>__0` variables. Consequence: **`Web.Host` still needs no CORS policy**, and adding one later would be a deliberate decision rather than a side effect
- WP-0.6: Tailwind **v4** (CSS-first `@theme`, `@tailwindcss/vite`, no `tailwind.config.js`); the DESIGN.md token table is transcribed once into `src/index.css` as CSS custom properties, with dark mode redefining only the neutrals
- WP-0.6: shadcn/ui components are hand-written into `src/components/ui/` in shadcn's own style rather than pulled by the CLI (deterministic, no network at build time); `components.json` is checked in so `npx shadcn@latest add` works for later WPs
- WP-0.6: the toast is **sonner** (shadcn's current toast) behind a `toast` facade in `components/feedback/toast.ts` — components never import sonner directly, so an API failure always reads the same way and a 403 renders as a permission message, not a crash
- WP-0.6: server state is TanStack Query with one typed client per module over a single `api` wrapper; the wrapper parses RFC 7807 into a typed `ApiError` and **never retries a 4xx**, since a 403 does not become a 200 on retry
- WP-0.6: the API client is React-free — the auth layer injects a token getter via `setAccessTokenProvider`, which is what puts the whole HTTP path in the fast tier
- WP-0.6: `ICurrentUser`'s browser counterpart is `/api/me`, not a decoded token — roles and permissions the UI shows on always match what the API will actually allow
- WP-0.6: the status **semantic map** (`components/ui/status.tsx`) is the one place a state-machine value becomes a colour; an unmapped status renders neutral rather than unstyled, so a module shipping a new state can never produce an invisible pill
- WP-0.6: all money, counts, percentages and timestamps go through `lib/format.ts` (DESIGN.md quality floor); `niceTicks` rounds chart axes so a graph reads $0/$1M/$2M/$3M rather than the data's raw maximum
- WP-0.6: the home route renders the reference dashboard from `features/dashboard/demo-data.ts` — static figures, fetched by nothing, so the design system is provable today. **WP-4.3 replaces that file with queries**; every other nav destination is an honest empty state naming the WP that fills it in
- WP-0.6: `docs/DESIGN.md` and `docs/SESSION.md` pointed at `docs/design/reference-dashboard.png`, which does not exist; both now point at the real file, `docs/Design.png`
- WP-0.6: the UI font is **Roboto**, not the Inter that DESIGN.md originally named (owner's call); `docs/DESIGN.md` updated in the same change. Weights 400/500/600/700 are all real Roboto instances, so nothing in the type scale is synthesised
- WP-0.6: scrollable panes carry `.scrollbar-subtle` — a thin thumb tinted to the surface it sits on (a lift of the sidebar on the dark sidebar, a canvas grey in the content column) rather than the browser's default light chrome bar, which stood out badly against `#14231C`. They also set `overflow-x: hidden`, because `overflow-y-auto` alone leaves the other axis at `auto` and a classic scrollbar narrowing the pane can produce a second, horizontal bar
- WP-0.6: the reference dashboard is richer than docs/Design.png's first cut (owner-supplied revision): KPI cards carry sparklines, the work-order feed is paginated with a filter/overflow header, procurement spend is a YTD/Budget/Variance stat row over a combined bar-and-line chart, and quick actions are a description list rather than square tiles. All of it still renders from `demo-data.ts` — WP-4.3 replaces the data, not the components
- WP-0.6: the spend chart's bars are **scaled into the line axis** rather than given a second one. Monthly spend is an order of magnitude below the running totals, so on a shared scale it is a smear along the baseline; the bars therefore carry no axis labels and read as shape only, and the axis belongs to the two cumulative lines. (Recharts 3 also silently drops one of two `YAxis` elements here, so a dual axis was not on offer.)
- WP-0.6: the sparkline is hand-drawn SVG, not Recharts — it has no axes, ticks or tooltips, and five chart instances in a KPI row would cost far more than they return
- WP-0.6: grid tracks are `minmax(0, 1fr)`, never bare `1fr`. A bare `1fr` track takes its content's min-content width as a floor, so one wide table or chart pushes the whole row past the viewport; `minmax(0, …)` lets the track shrink and the card's own overflow rules take over
- WP-0.6: the three-across card rows are a **2xl** layout, two-across at the 1280 floor — three cards of ~310px wrap their titles and hide half the feed table. The reference screenshot is a ~1780px viewport, which is where the three-across look applies
- WP-0.6: `--chart-5` (the neutral categorical colour) is redefined in dark mode. It is a light grey by design, which on a dark card is the loudest thing in the chart; the other four hues hold, per DESIGN.md
- WP-0.6: the access token is published to the API client **during render**, not from an effect. A child's mount effect runs before its parent's, so an effect in the token bridge let the shell's first `/api/me` leave without an Authorization header and 401 — which the query client correctly refuses to retry, leaving the sidebar with no account for the life of the session
- WP-0.6: every request carries a 15s timeout (`requestTimeoutMs`, overridable per call) combined with the caller's own signal. A stalled connection previously left the UI in its loading state forever, which reads as a broken screen rather than an error anyone can act on; a stall now arrives as `ApiError.isUnreachable`, which is retryable because it is not a 4xx. The timeout is matched on the exception's `name`, not `instanceof DOMException` — that exception crosses realms and the name is the part the platform guarantees
- WP-0.6: a loading or failing state fills in a control's **text**, it never replaces the control. The sidebar account menu is the case that proved it: replacing the whole button with a skeleton meant a slow `/api/me` also removed the only way to sign out
- WP-0.6: the dev-server proxy target resolution moved to `web/src/lib/api-target.ts` and is unit-tested. Its old fallback pointed at a port nothing listens on (`https://localhost:7443`); it is now the Web.Host `http` launch profile (`http://localhost:5273`), so `npm run dev` outside the AppHost reaches a real host
- WP-0.6: `vite.config.ts` prints the resolved `/api` target and the OIDC authority on every dev start, and logs proxy errors and 4xx/5xx responses. A proxy failure is otherwise completely silent — the browser request just hangs with no status — and "where does /api go" is the first question when the SPA loads but every request fails

- WP-0.7: CI is GitHub Actions in three jobs — `dotnet-unit` and `web` run in parallel on every push and PR, `integration` runs behind both. Each job builds what it needs rather than a `build` job shipping output through an artifact: on a hosted runner the upload/download round-trip for .NET build output costs more than the rebuild it saves, and the fast jobs then depend on nothing
- WP-0.7: the unit job passes `-- RunConfiguration.MaxCpuCount=0` (one worker per core). VSTest runs test assemblies sequentially by default, so twelve unit projects would have run one after another even though xUnit parallelises within each — the opposite of CONVENTIONS.md rule A, and invisible without the flag
- WP-0.7: `tests/Build.UnitTests` added — a fast test project that asserts on the repo's own build and CI configuration (no product reference). Workflow files, `.slnf` filters and Dependabot rules are not compiled, so a mistake in them is discovered as a suite that quietly skips projects or takes an hour; these are the assertions that notice. Guards proven by mutation, not just by passing
- WP-0.7: the `*.UnitTests` ↔ `tests/UnitTests.slnf` registration trap (STATUS's standing warning) is now a test rather than a note. `.slnf` is JSON with escaped Windows separators, so the filter is **parsed**, not string-matched against the file's raw text
- WP-0.7: assertions that a flag is *absent* from a workflow read the YAML with comment lines stripped (`RepositoryFiles.ReadYamlDirectives`) — the comments in these files name the flags they warn against, and a test that trips over the warning instead of the mistake is worse than no test. Found by writing the test and watching it fail on its own comment
- WP-0.7: the gate tier is **one** xUnit collection (`GateCollection`) for the whole suite, not one per class. xUnit 2.x has no assembly-level fixture, so a single collection plus the existing `parallelizeTestCollections: false` is what makes "one container set per run" (CONVENTIONS.md rule D) actually true, and it is also what lets a Respawn reset run without wiping the database under a concurrent test
- WP-0.7: `GateFixture` starts Postgres, RabbitMQ **and Redis** and boots the real `Web.Host` through `WebApplicationFactory<Program>` — the shipped composition, not a hand-assembled subset, so a composition mistake (a consumer registered after the bus, a missing connection string) fails a test instead of `aspire run`. WP-0.5's separate `OutboxFixture` and its second container pair are gone
- WP-0.7: the gate fixture configures the host with **environment variables**, not `ConfigureAppConfiguration`. Under minimal hosting `Program.cs` reads `builder.Configuration` while it composes the app, which is before a test host's configuration callbacks run — the connection strings arrived after the host had already thrown for the lack of them. Environment variables are also how the AppHost and a deploy supply these, so the gate tier feeds the host the way the real world does
- WP-0.7: Respawn wipes application data but **ignores** MassTransit's outbox/inbox tables and `platform.processed_messages`. A long-lived background service owns them for the whole run, and `TRUNCATE` needs an exclusive lock on a table the delivery service is polling — a flake generator that buys nothing, because every event carries a fresh Guid v7 id and tests isolate on that id rather than on an empty table
- WP-0.7: every `__ef_migrations_history` table is discovered from `information_schema` rather than listed, so a module whose schema lands in a later WP is protected the day it appears with nothing here to remember to update
- WP-0.7: images are published by the **.NET SDK's own container publishing** (`/t:PublishContainer`) to GHCR, on a `v*` tag only — no Dockerfile is checked in, so there is nothing to keep in step with the csproj. The SPA's tag build uploads `web/dist` as an artifact rather than inventing a static-hosting image, which is WP-5.1/5.2's design to make
- WP-0.7: Dependabot holds MassTransit at `>=9.0.0` for all three packages, and a unit test asserts both the pin and the hold. The 8.x pin was WP-0.5's licensing decision; without the hold, one merged bot PR relicenses the messaging layer
- WP-0.7: **ESLint is not installable on this repo, and the linter is `oxlint`.** `typescript@7` is the native compiler — its npm package exports only `{ version, versionMajorMinor }`, with no `createSourceFile`/`createProgram` — so typescript-eslint (peer `typescript <6.1.0`) cannot parse a single file, and without it ESLint cannot read `.ts`/`.tsx` at all. oxlint brings its own parser, needs no `typescript`, runs the whole SPA in ~0.3s and found five real defects in WP-0.6 code on its first run. Revisit ESLint when typescript-eslint ships TS 7 support; `npm run lint` is `oxlint && tsc -b --noEmit`, and the type check stays because oxlint is type-unaware
- WP-0.7: `react/react-in-jsx-scope` is off — React 19 with the automatic JSX runtime never references `React` by name, so the pre-17 rule is pure noise
- WP-0.7: CI needs **no** `dotnet new install Aspire.ProjectTemplates` (STATUS's open question). Templates are for scaffolding; the AppHost's `Sdk="Aspire.AppHost.Sdk/13.5.2"` resolves from nuget.org during restore. Verified with a cold restore into an empty package folder
- WP-0.7: Node is pinned by `web/.nvmrc` (24) and CI reads the version from that file, so the runner and a developer's `nvm use` cannot drift apart

- WP-0.8: **reference data ships as `HasData` in each module's `IEntityTypeConfiguration`**, not as a bootstrap service that upserts at startup. A migrated database therefore has a chart of accounts, tariffs and warehouses in *every* environment with no code running — which is what invariant 8 actually asks for — and changing a reference row is a new migration rather than an edit that silently diverges between deployments
- WP-0.8: reference rows get **deterministic version 7 ids** derived from a fixed authoring instant plus their own natural key (`Platform/Data/ReferenceId.cs`). `Guid.CreateVersion7(now)` cannot be used in seed data: EF compares seeded rows against the model snapshot, so a fresh id per model build would rewrite the whole chart of accounts on every `migrations add`. Natural-key primary keys were the alternative and were rejected — CONVENTIONS.md says ids are Guid v7, and a derived id is still one by layout, so the primary-key index still orders chronologically alongside runtime rows
- WP-0.8: the chart of accounts is 15 accounts covering all five account types — the ones the two demonstration workflows post to plus what a trial balance needs to look like one. `FinanceAccounts` keeps the code constants (moved to `Features/ChartOfAccounts/`) and a fast test asserts every code it names, and every code the event seam posts to, exists in the chart. That closes the placeholder loop WP-0.5 opened
- WP-0.8: `Account.NormalBalance` is **derived from `AccountType`**, not stored. A column could disagree with the account's own kind and nothing would notice until a trial balance came out backwards
- WP-0.8: two tariffs ship, not one — residential inclining-block (the default) and commercial declining-block — so WP-2.3's rate engine has both shapes to get right, and so "the default plan" is visibly a property of a plan rather than of the system. A filtered unique index (`ux_rate_plans_default`) makes "exactly one default" a database fact
- WP-0.8: tier rules live in a pure `RatePlanTiers.Validate` (1..n without gaps, each block ending above the last, the last one unbounded, no negative rates) and the *shipped* plans are validated by it at type-initialisation time. A malformed tariff is otherwise discovered by the first bill run, on a customer's statement
- WP-0.8: **roles stay in the Keycloak realm plus `RolePermissionMap`** — the WP text lists them as reference data, but bootstrapping a `roles` table would create a second source of truth for something WP-0.3 already settled, and endpoints are gated on permissions rather than role rows. WP-4.5's admin surface reads the existing map
- WP-0.8: warehouses land now (in Inventory's new schema) rather than waiting for WP-1.4, because stock cannot be received or issued without somewhere to be; codes are forced upper case at construction so "main" and "MAIN" can never become two warehouses holding half the stock each
- WP-0.8: the demo seeder is a per-module `IDemoSeeder` seam (`Name`, `Order`, `SeedAsync`) registered with `services.AddDemoSeeder<T>()` and run once at startup by `DemoSeedRunner`. Idempotency is a `platform.demo_seed_records` row keyed on the seeder's name, written **in the same `IUnitOfWork` transaction as the data**, so a seeder that throws half way leaves neither its rows nor its record and the next start genuinely retries. `Name` is a dedupe key and is never renamed
- WP-0.8: the demo guard is deliberately **asymmetric** — `Platform:SeedDemoData` can turn seeding off in Development but no configuration turns it on anywhere else, and `DemoSeedRunner` re-checks the environment and throws even if something registered it. Demo data invents customers, meters and bills; the damage of one seeding a real database is not undone by deleting rows
- WP-0.8: the one seeder shipping today is `ApprovalQueueDemoSeeder` (a pending purchase order and a pending bill adjustment). The modules whose demo data SPEC.md lists do not have entities yet, and inventing them here would trespass on WP-1.x/2.x; the approval primitive is module-agnostic by design, so it is the one thing that *can* be demonstrated now. Later WPs add their own seeders and this one's rows become real ones
- WP-0.8: seeded rows are attributed to `DemoActor`s (`demo:warehouse`, `demo:billing`) rather than to the system or to a real subject id. Separation of duties refuses a decision by whoever raised the request, so a queue raised by the signed-in user would refuse every decision and look broken; the `demo:` prefix cannot collide with an identity-provider subject, and the actor holds no permissions at all
- WP-0.8: `PlatformDatabaseInitializer` is now `GridCoreDatabaseInitializer` and migrates **every** context registered with `AddGridCoreDbContext` (discovered through the `UnitOfWorkParticipant` registrations), not just the platform's. A module's schema is then migrated the day it appears, with nothing to remember to update
- WP-0.8: the `UseNpgsql` + `MigrationsHistoryTable` triple every context repeats in three places (module registration, design-time factory, gate fixture) is now `GridCoreDbContexts.InSchema(schema)`
- WP-0.8: the gate fixture's Respawn reset **ignores tables holding migration-seeded rows**, discovered from each context's *design-time* model via `GetSeedData()` (the runtime model strips seed data out). Truncating them would delete reference data that only a migration puts back — and that migration is already recorded as applied — so the second test in a run would find an empty chart of accounts and blame itself
