# DECISIONS.md — Utility ERP

> One line per settled choice. Appended by Claude each session; not relitigated without a WP.

- Bootstrap: modular monolith (ASP.NET Core + Aspire), schema-per-module, events for cross-module effects
- Bootstrap: no Python — this project has no polling/monitoring need (unlike ITMS)
- Bootstrap: external systems simulated behind provider interfaces (IMeterReadingProvider, IPaymentProvider, IVendorProvider, ICrewProvider) from day one
- Bootstrap: Finance is downstream-only — consumes events, posts balanced journal entries, never calls back
- Bootstrap: money is decimal; ledger append-only; corrections are new entries
- Bootstrap: TEST SPEED is a first-class requirement — fast unit pyramid, shared Testcontainer+Respawn for integration, parallel, never --maxcpucount:1 (fixes ITMS slowness)
- Bootstrap: UI = Tailwind + shadcn + lucide per DESIGN.md reference dashboard
- WP-0.1: assembly/namespace prefix is `GridCore` (`GridCore.Modules.<Name>`, `GridCore.Platform`, …); solution file is `GridCore.slnx` (.NET 10 XML format)
- WP-0.1: central package management (`Directory.Packages.props`) + shared `Directory.Build.props` — one place for net10.0, nullable, warnings-as-errors and the xUnit stack; test projects are identified by an `*Tests` name suffix because `IsTestProject` is set too late for a props-file condition
- WP-0.1: modules compose via a `Platform.Modules.IModule` seam (`Name`/`AddServices`/`MapEndpoints`), listed explicitly in `Web.Host/Program.cs` rather than assembly-scanned
- WP-0.1: Aspire `ServiceDefaults` project added alongside `AppHost` (standard Aspire pair; consumed by Web.Host from WP-0.2)
- WP-0.1: fast loop runs `tests/UnitTests.slnf` — `dotnet test` accepts only one project/solution argument, so the documented `tests/*UnitTests` glob was corrected in CONVENTIONS.md
- WP-0.1: no assertion library beyond xUnit's `Assert` (FluentAssertions deliberately not added — 8.x is commercially licensed)
- WP-0.2: `aspire.config.json` lives at the repository root (pointing at `src/AppHost`) so `aspire run` resolves the AppHost from anywhere in a fresh clone
- WP-0.2: AppHost composition lives in `InfrastructureComposition`/`WebComposition` extension methods rather than inline in `AppHost.cs`, so the application model is unit-testable in the fast tier without Docker (`tests/AppHost.UnitTests`)
- WP-0.2: MinIO is composed as a pinned plain `AddContainer` (`minio/minio:RELEASE.2025-09-07T16-13-09Z`) — there is no first-party Aspire integration and the community-toolkit package ships pre-release only; never `latest`, which would change the object store under a demo
- WP-0.2: Keycloak uses the official `Aspire.Hosting.Keycloak` 13.5.2-preview — preview is the only channel Microsoft ships it on; its version tracks the rest of Aspire
- WP-0.2: `AddNpmApp` no longer exists in Aspire 13 (`Aspire.Hosting.NodeJs` → `Aspire.Hosting.JavaScript`); the WP-0.2 spec's "web dev server via AddNpmApp" is implemented as `AddViteApp(...).WithNpm()`
- WP-0.2: the React dev-server resource is skipped when `web/` is absent, so `aspire run` stays green until WP-0.6 creates it
- WP-0.2: infra credentials come from named `Parameters:` in `src/AppHost/appsettings.Development.json` (checked in, dev-only) because Postgres/RabbitMQ/Keycloak/MinIO persist their users into their data volumes — a per-run generated password would lock the AppHost out of the volume it created last run. Production supplies the same parameter names from the environment; Redis keeps Aspire's generated password since no user is persisted in its volume
- WP-0.2: `/health` aggregation comes from the Aspire client integrations registered in `Web.Host` (Aspire.Npgsql, Aspire.StackExchange.Redis, Aspire.RabbitMQ.Client); consequence — `Web.Host` no longer starts standalone, it requires the AppHost-supplied connection strings
- WP-0.3: authentication is plain `AddJwtBearer` bound to an `Authentication:*` section (Authority/Audience/RequireHttpsMetadata/RolesClaimPath/NameClaimType), NOT the Keycloak-specific Aspire client integration — swapping OIDC provider is then a configuration change with no code change, as the WP requires
- WP-0.3: endpoints are gated on **permissions**, never on role names; `RolePermissionMap` is the single place roles become permissions, so re-cutting a role touches one file. `Permissions.All` is discovered by reflection over the constants so a new permission can never be missing from the Administrator grant
- WP-0.3: permission policies are built on demand by `PermissionPolicyProvider` for any `perm:<permission>` policy name (`.RequirePermission(Permissions.Billing.Adjust)`), rather than registering a named policy per permission at startup
- WP-0.3: the host is **secure by default** — a fallback policy requires an authenticated caller, so a new module endpoint cannot ship accidentally public; `/health` and `/alive` in ServiceDefaults opt out with `AllowAnonymous` because Aspire's probes carry no token
- WP-0.3: role claims are normalised to `ClaimTypes.Role` by `GridCoreClaimsTransformation` reading a configured dotted path (`realm_access.roles` for Keycloak, a flat `roles` claim for other providers); an unreadable claim yields no roles rather than an exception, so a token GridCore cannot parse means no access, never a 500
- WP-0.3: roles the realm does not define are ignored rather than rejected — the IdP may carry roles for other systems (`offline_access`, `default-roles-*`) and an unknown role must never widen access
- WP-0.3: the Keycloak realm is checked in as `src/AppHost/keycloak/realms/gridcore-realm.json` and imported **in Development only**, because it carries eight test users with a well-known password; a production realm (same roles and clients, real users) is WP-5.1's to supply
- WP-0.3: `gridcore-web` is a public PKCE client whose audience mapper targets `gridcore-api`; direct access grants stay enabled in the dev realm so the RBAC checks can fetch a token with curl
- WP-0.3: `Web.Host` registers `AddProblemDetails()` + `UseStatusCodePages()` so the framework's own 401/403 carry RFC 7807 bodies, per CONVENTIONS.md
- WP-0.4: EF Core 10 + Npgsql lands here (the first WP that persists anything); `Platform` owns the `platform` schema through `PlatformDbContext`, registered as a plain `AddDbContext`/`UseNpgsql` rather than an Aspire client integration — Platform is a library and must not depend on Aspire; `/health`'s Postgres check stays WP-0.2's `AddNpgsqlDataSource`
- WP-0.4: tables and columns are named explicitly in `IEntityTypeConfiguration` classes rather than adding `EFCore.NamingConventions` — snake_case per CONVENTIONS.md with one fewer dependency; primary keys and indexes are named too (`pk_`/`ix_`) so migrations read the same as the database
- WP-0.4: JSON snapshots are `jsonb` on Postgres; `PlatformDbContext.OnModelCreating` relaxes that column type for non-Npgsql providers so the fast tier runs the *same* model on SQLite in-memory (CONVENTIONS.md rule C) instead of a second model or a container
- WP-0.4: queries order by the Guid v7 primary key, not by the timestamp column — v7 ids sort chronologically as `uuid` on Postgres and as TEXT on SQLite, it reuses the PK index, and SQLite cannot `ORDER BY` a `DateTimeOffset` at all
- WP-0.4: audit snapshots serialise enums by name (`JsonStringEnumConverter`); an entry read years later must not depend on today's enum numbering. The `status` column is stored by name for the same reason
- WP-0.4: `IAuditLog` has two one-liners — `Record` enlists the entry in the current platform unit of work so it commits in the same transaction as the change it describes, `RecordAsync` also saves for writes with no shared unit of work. Cross-context atomicity (a module's DbContext + the platform's) is WP-0.5's to settle alongside the outbox
- WP-0.4: the audit trail is append-only in code — `PlatformDbContext.SaveChanges(Async)` throws if an `AuditEntry` is Modified or Deleted, the same rule the ledger will follow
- WP-0.4: `ICurrentUser` (with `HttpContextCurrentUser` and `SystemUser`) is the seam for "who is acting"; audit and services take it instead of `IHttpContextAccessor` or raw claims. Outside a request the actor is `system` (and is not user-gated, since background work is the host's own); an anonymous caller *inside* a request holds nothing
- WP-0.4: the approval primitive carries its own `RequiredPermission`, checked in `ApprovalService` rather than at the edge — `platform.approve` gets a caller into the queue, the request's own permission decides whether they may decide *that* one, so a PO and a bill adjustment share one table and one workflow
- WP-0.4: separation of duties is enforced in the aggregate — a request may not be decided by whoever raised it, and only the requester may withdraw it; decisions are final (a re-decision means a new request), matching the append-only ledger rule
- WP-0.4: the scheduler is a plain `BackgroundService` over an `IScheduledJob` seam (per-job loop, per-run DI scope, `TimeProvider` for the delay, failures logged and survived) — no Quartz/Hangfire, which the MVP does not need
- WP-0.4: the notification stub is `INotificationSender` + `LoggingNotificationSender`, swapped by DI exactly like the provider interfaces
- WP-0.4: migrations are applied at startup by `PlatformDatabaseInitializer` in Development only (overridable with `Platform:ApplyMigrationsAtStartup`); a production deploy migrates as its own step — WP-5.1's
- WP-0.4: FluentValidation is still not referenced — WP-0.4's edge validation is the aggregate's own guards surfaced as ProblemDetails. The FluentValidation pattern CONVENTIONS.md prescribes lands with the first real CRUD slice (WP-1.1), which is where a validator registration convention belongs
- WP-0.4: `.editorconfig` exempts `**/Data/Migrations/*.cs` from code style — EF writes those files (block namespaces) and they are append-only, never hand-edited
- WP-0.5: MassTransit is pinned to **8.5.10**, the last Apache-2.0 line — 9.x moved to a commercial licence (its nuspec points at massient.com/license instead of carrying an SPDX expression). 8.5.10 ships a first-class `net10.0` target, so nothing is given up. **Never bump to 9.x**; the pin and the reason live in `Directory.Packages.props`
- WP-0.5: MassTransit's **EF transactional outbox** is used rather than a hand-rolled one, and it lives in `PlatformDbContext` (the `platform` schema) so every module publishes into one outbox; `UseBusOutbox()` means `IPublishEndpoint` writes a row instead of reaching the broker
- WP-0.5: the outbox/inbox tables are renamed to snake_case (`inbox_state`, `outbox_message`, `outbox_state`) but their **columns keep MassTransit's PascalCase names** — the library queries its own model, so renaming columns buys nothing and adds a migration to get wrong
- WP-0.5: modules never see MassTransit. Publishing is `IEventPublisher.PublishAsync`; consuming is deriving `IdempotentConsumer<TEvent>`. Swapping transport is a Platform change, and the consume path is testable without a bus
- WP-0.5: **cross-context atomicity** (owed by WP-0.4) is solved with a per-scope shared `DbConnection` (`GridCoreDbConnection`) plus `IUnitOfWork.ExecuteAsync`. Contexts register with `AddGridCoreDbContext<T>`, which also enlists them as `UnitOfWorkParticipant`s; the unit of work attaches every participant to one transaction *before* the delegate runs, saves them all, then commits. A module write, its audit entry and its outbox row are therefore one transaction across three schemas
- WP-0.5: participants are resolved lazily (only when a transaction actually starts) but **all** of them are attached, not just the ones already touched — a context first used inside the delegate would otherwise silently open its own transaction
- WP-0.5: consumer idempotency is GridCore's own `IMessageDeduplicator` over `platform.processed_messages`, keyed on (message, consumer) so several modules may each react once to the same event. MassTransit's inbox filter is deliberately not enabled — one dedupe mechanism, and it is the one ARCHITECTURE.md names
- WP-0.5: the dedupe read-then-insert takes no lock. Two racing deliveries both insert, the composite PK rejects the loser, its transaction rolls back and the broker redelivers it — one wasted redelivery beats a lock on every message
- WP-0.5: the claim is written in the same transaction as the consumer's work, so a consumer that throws leaves no claim behind and the redelivery genuinely retries instead of being skipped as done
- WP-0.5: `IdempotentEventHandler` (unit of work + dedupe + run) is free of MassTransit types, and `IdempotentConsumer<TEvent>` is a three-line adapter over it — that is what puts the whole consume path in the fast tier
- WP-0.5: events are positional records with a static `For(...)` factory that stamps `Guid.CreateVersion7(occurredAt)`, matching `AuditEntry.For`/`ApprovalRequest.Raise`. The publisher refuses an event with an empty `EventId`, because a message no consumer can deduplicate is a double posting waiting to happen
- WP-0.5: Finance's seam is `IJournalPostingSeam` with a `LoggingJournalPostingSeam` no-op, swapped by DI exactly like the notification stub. The mapping to double entry (`FinancePostings`) is pure and **already balanced-or-throw** (`JournalPostingIntent.For`), so invariant 3 is enforced from today even though the ledger itself is WP-2.6's
- WP-0.5: `FinanceAccounts` holds placeholder account codes (1000/1100/1300/2000/4000) until WP-0.8 ships the chart of accounts by migration and WP-2.6 looks codes up against it
- WP-0.5: `AddGridCoreMessaging` is called **after** `AddModules` in `Program.cs` and reads the consumers back off the `IServiceCollection` (the `AddScheduledJob` trick) — the bus composition stays explicit, nothing is assembly-scanned
- WP-0.5: a missing `rabbitmq` connection string throws a named `InvalidOperationException` at startup, matching the platform schema's behaviour — a host that boots without a broker would accept writes and silently never deliver their events
- WP-0.5: `tests/Contracts.UnitTests` added (first project to test `Contracts`), registered in both `GridCore.slnx` and `tests/UnitTests.slnf`
- WP-0.5: the gate-tier `OutboxFixture` starts **one** Postgres and **one** RabbitMQ container for the whole messaging collection and applies migrations once, per CONVENTIONS.md rule D. It is deliberately minimal — WP-0.7 owns generalising it (and adding Respawn) for the rest of the gate suite

- WP-0.6: the SPA is Vite + React 19 + TypeScript in `web/`, hosted by the AppHost's existing `AddViteApp` resource; the dev server is served **unproxied on a fixed 5173** (`WebComposition.WebAppPort` + `strictPort` in `vite.config.ts`) because the Keycloak realm registers `gridcore-web` at `http://localhost:5173` — a drifting port is a rejected `redirect_uri`, not a warning
- WP-0.6: Aspire's **default proxied endpoint is wrong for an OIDC SPA** — it fronts the dev server on a randomly allocated port, so the browser's origin (and therefore its `redirect_uri`) changes every run and Keycloak refuses the login. `WithGridCoreWebAppEndpoint` sets `Port`/`TargetPort` and `IsProxied = false`; unit tests assert the AppHost port, the realm export's registered URIs and `vite.config.ts` all agree, because the failure only shows up at login time
- WP-0.6: OIDC in the browser is `react-oidc-context` + `oidc-client-ts` (Authorization Code + PKCE against the public `gridcore-web` client). Tokens live in **sessionStorage**, not localStorage, so closing the tab ends the session
- WP-0.6: the AppHost hands the SPA `VITE_OIDC_AUTHORITY/CLIENT_ID/AUDIENCE` (`WithGridCoreWebAppConfiguration`), built from the *same* `ReferenceExpression` as the API's `Authentication__Authority` — a unit test asserts the two are equal, because a different host for login than for validation fails issuer matching silently
- WP-0.6: the browser reaches the API same-origin through Vite's `/api` proxy, whose target comes from Aspire's `services__web-host__<scheme>__0` variables. Consequence: **`Web.Host` still needs no CORS policy**, and adding one later would be a deliberate decision rather than a side effect
- WP-0.6: Tailwind **v4** (CSS-first `@theme`, `@tailwindcss/vite`, no `tailwind.config.js`); the DESIGN.md token table is transcribed once into `src/index.css` as CSS custom properties, with dark mode redefining only the neutrals
- WP-0.6: shadcn/ui components are hand-written into `src/components/ui/` in shadcn's own style rather than pulled by the CLI (deterministic, no network at build time); `components.json` is checked in so `npx shadcn@latest add` works for later WPs
- WP-0.6: the toast is **sonner** (shadcn's current toast) behind a `toast` facade in `components/feedback/toast.ts` — components never import sonner directly, so an API failure always reads the same way and a 403 renders as a permission message, not a crash
- WP-0.6: server state is TanStack Query with one typed client per module over a single `api` wrapper; the wrapper parses RFC 7807 into a typed `ApiError` and **never retries a 4xx**, since a 403 does not become a 200 on retry
- WP-0.6: the API client is React-free — the auth layer injects a token getter via `setAccessTokenProvider`, which is what puts the whole HTTP path in the fast tier
- WP-0.6: `ICurrentUser`'s browser counterpart is `/api/me`, not a decoded token — roles and permissions the UI shows on always match what the API will actually allow
- WP-0.6: the status **semantic map** (`components/ui/status.tsx`) is the one place a state-machine value becomes a colour; an unmapped status renders neutral rather than unstyled, so a module shipping a new state can never produce an invisible pill
- WP-0.6: all money, counts, percentages and timestamps go through `lib/format.ts` (DESIGN.md quality floor); `niceTicks` rounds chart axes so a graph reads $0/$1M/$2M/$3M rather than the data's raw maximum
- WP-0.6: the home route renders the reference dashboard from `features/dashboard/demo-data.ts` — static figures, fetched by nothing, so the design system is provable today. **WP-4.3 replaces that file with queries**; every other nav destination is an honest empty state naming the WP that fills it in
- WP-0.6: `docs/DESIGN.md` and `docs/SESSION.md` pointed at `docs/design/reference-dashboard.png`, which does not exist; both now point at the real file, `docs/Design.png`
- WP-0.6: the UI font is **Roboto**, not the Inter that DESIGN.md originally named (owner's call); `docs/DESIGN.md` updated in the same change. Weights 400/500/600/700 are all real Roboto instances, so nothing in the type scale is synthesised
- WP-0.6: scrollable panes carry `.scrollbar-subtle` — a thin thumb tinted to the surface it sits on (a lift of the sidebar on the dark sidebar, a canvas grey in the content column) rather than the browser's default light chrome bar, which stood out badly against `#14231C`. They also set `overflow-x: hidden`, because `overflow-y-auto` alone leaves the other axis at `auto` and a classic scrollbar narrowing the pane can produce a second, horizontal bar
- WP-0.6: the reference dashboard is richer than docs/Design.png's first cut (owner-supplied revision): KPI cards carry sparklines, the work-order feed is paginated with a filter/overflow header, procurement spend is a YTD/Budget/Variance stat row over a combined bar-and-line chart, and quick actions are a description list rather than square tiles. All of it still renders from `demo-data.ts` — WP-4.3 replaces the data, not the components
- WP-0.6: the spend chart's bars are **scaled into the line axis** rather than given a second one. Monthly spend is an order of magnitude below the running totals, so on a shared scale it is a smear along the baseline; the bars therefore carry no axis labels and read as shape only, and the axis belongs to the two cumulative lines. (Recharts 3 also silently drops one of two `YAxis` elements here, so a dual axis was not on offer.)
- WP-0.6: the sparkline is hand-drawn SVG, not Recharts — it has no axes, ticks or tooltips, and five chart instances in a KPI row would cost far more than they return
- WP-0.6: grid tracks are `minmax(0, 1fr)`, never bare `1fr`. A bare `1fr` track takes its content's min-content width as a floor, so one wide table or chart pushes the whole row past the viewport; `minmax(0, …)` lets the track shrink and the card's own overflow rules take over
- WP-0.6: the three-across card rows are a **2xl** layout, two-across at the 1280 floor — three cards of ~310px wrap their titles and hide half the feed table. The reference screenshot is a ~1780px viewport, which is where the three-across look applies
- WP-0.6: `--chart-5` (the neutral categorical colour) is redefined in dark mode. It is a light grey by design, which on a dark card is the loudest thing in the chart; the other four hues hold, per DESIGN.md
- WP-0.6: the access token is published to the API client **during render**, not from an effect. A child's mount effect runs before its parent's, so an effect in the token bridge let the shell's first `/api/me` leave without an Authorization header and 401 — which the query client correctly refuses to retry, leaving the sidebar with no account for the life of the session
- WP-0.6: every request carries a 15s timeout (`requestTimeoutMs`, overridable per call) combined with the caller's own signal. A stalled connection previously left the UI in its loading state forever, which reads as a broken screen rather than an error anyone can act on; a stall now arrives as `ApiError.isUnreachable`, which is retryable because it is not a 4xx. The timeout is matched on the exception's `name`, not `instanceof DOMException` — that exception crosses realms and the name is the part the platform guarantees
- WP-0.6: a loading or failing state fills in a control's **text**, it never replaces the control. The sidebar account menu is the case that proved it: replacing the whole button with a skeleton meant a slow `/api/me` also removed the only way to sign out
- WP-0.6: the dev-server proxy target resolution moved to `web/src/lib/api-target.ts` and is unit-tested. Its old fallback pointed at a port nothing listens on (`https://localhost:7443`); it is now the Web.Host `http` launch profile (`http://localhost:5273`), so `npm run dev` outside the AppHost reaches a real host
- WP-0.6: `vite.config.ts` prints the resolved `/api` target and the OIDC authority on every dev start, and logs proxy errors and 4xx/5xx responses. A proxy failure is otherwise completely silent — the browser request just hangs with no status — and "where does /api go" is the first question when the SPA loads but every request fails

- WP-0.7: CI is GitHub Actions in three jobs — `dotnet-unit` and `web` run in parallel on every push and PR, `integration` runs behind both. Each job builds what it needs rather than a `build` job shipping output through an artifact: on a hosted runner the upload/download round-trip for .NET build output costs more than the rebuild it saves, and the fast jobs then depend on nothing
- WP-0.7: the unit job passes `-- RunConfiguration.MaxCpuCount=0` (one worker per core). VSTest runs test assemblies sequentially by default, so twelve unit projects would have run one after another even though xUnit parallelises within each — the opposite of CONVENTIONS.md rule A, and invisible without the flag
- WP-0.7: `tests/Build.UnitTests` added — a fast test project that asserts on the repo's own build and CI configuration (no product reference). Workflow files, `.slnf` filters and Dependabot rules are not compiled, so a mistake in them is discovered as a suite that quietly skips projects or takes an hour; these are the assertions that notice. Guards proven by mutation, not just by passing
- WP-0.7: the `*.UnitTests` ↔ `tests/UnitTests.slnf` registration trap (STATUS's standing warning) is now a test rather than a note. `.slnf` is JSON with escaped Windows separators, so the filter is **parsed**, not string-matched against the file's raw text
- WP-0.7: assertions that a flag is *absent* from a workflow read the YAML with comment lines stripped (`RepositoryFiles.ReadYamlDirectives`) — the comments in these files name the flags they warn against, and a test that trips over the warning instead of the mistake is worse than no test. Found by writing the test and watching it fail on its own comment
- WP-0.7: the gate tier is **one** xUnit collection (`GateCollection`) for the whole suite, not one per class. xUnit 2.x has no assembly-level fixture, so a single collection plus the existing `parallelizeTestCollections: false` is what makes "one container set per run" (CONVENTIONS.md rule D) actually true, and it is also what lets a Respawn reset run without wiping the database under a concurrent test
- WP-0.7: `GateFixture` starts Postgres, RabbitMQ **and Redis** and boots the real `Web.Host` through `WebApplicationFactory<Program>` — the shipped composition, not a hand-assembled subset, so a composition mistake (a consumer registered after the bus, a missing connection string) fails a test instead of `aspire run`. WP-0.5's separate `OutboxFixture` and its second container pair are gone
- WP-0.7: the gate fixture configures the host with **environment variables**, not `ConfigureAppConfiguration`. Under minimal hosting `Program.cs` reads `builder.Configuration` while it composes the app, which is before a test host's configuration callbacks run — the connection strings arrived after the host had already thrown for the lack of them. Environment variables are also how the AppHost and a deploy supply these, so the gate tier feeds the host the way the real world does
- WP-0.7: Respawn wipes application data but **ignores** MassTransit's outbox/inbox tables and `platform.processed_messages`. A long-lived background service owns them for the whole run, and `TRUNCATE` needs an exclusive lock on a table the delivery service is polling — a flake generator that buys nothing, because every event carries a fresh Guid v7 id and tests isolate on that id rather than on an empty table
- WP-0.7: every `__ef_migrations_history` table is discovered from `information_schema` rather than listed, so a module whose schema lands in a later WP is protected the day it appears with nothing here to remember to update
- WP-0.7: images are published by the **.NET SDK's own container publishing** (`/t:PublishContainer`) to GHCR, on a `v*` tag only — no Dockerfile is checked in, so there is nothing to keep in step with the csproj. The SPA's tag build uploads `web/dist` as an artifact rather than inventing a static-hosting image, which is WP-5.1/5.2's design to make
- WP-0.7: Dependabot holds MassTransit at `>=9.0.0` for all three packages, and a unit test asserts both the pin and the hold. The 8.x pin was WP-0.5's licensing decision; without the hold, one merged bot PR relicenses the messaging layer
- WP-0.7: **ESLint is not installable on this repo, and the linter is `oxlint`.** `typescript@7` is the native compiler — its npm package exports only `{ version, versionMajorMinor }`, with no `createSourceFile`/`createProgram` — so typescript-eslint (peer `typescript <6.1.0`) cannot parse a single file, and without it ESLint cannot read `.ts`/`.tsx` at all. oxlint brings its own parser, needs no `typescript`, runs the whole SPA in ~0.3s and found five real defects in WP-0.6 code on its first run. Revisit ESLint when typescript-eslint ships TS 7 support; `npm run lint` is `oxlint && tsc -b --noEmit`, and the type check stays because oxlint is type-unaware
- WP-0.7: `react/react-in-jsx-scope` is off — React 19 with the automatic JSX runtime never references `React` by name, so the pre-17 rule is pure noise
- WP-0.7: CI needs **no** `dotnet new install Aspire.ProjectTemplates` (STATUS's open question). Templates are for scaffolding; the AppHost's `Sdk="Aspire.AppHost.Sdk/13.5.2"` resolves from nuget.org during restore. Verified with a cold restore into an empty package folder
- WP-0.7: Node is pinned by `web/.nvmrc` (24) and CI reads the version from that file, so the runner and a developer's `nvm use` cannot drift apart

- WP-0.8: **reference data ships as `HasData` in each module's `IEntityTypeConfiguration`**, not as a bootstrap service that upserts at startup. A migrated database therefore has a chart of accounts, tariffs and warehouses in *every* environment with no code running — which is what invariant 8 actually asks for — and changing a reference row is a new migration rather than an edit that silently diverges between deployments
- WP-0.8: reference rows get **deterministic version 7 ids** derived from a fixed authoring instant plus their own natural key (`Platform/Data/ReferenceId.cs`). `Guid.CreateVersion7(now)` cannot be used in seed data: EF compares seeded rows against the model snapshot, so a fresh id per model build would rewrite the whole chart of accounts on every `migrations add`. Natural-key primary keys were the alternative and were rejected — CONVENTIONS.md says ids are Guid v7, and a derived id is still one by layout, so the primary-key index still orders chronologically alongside runtime rows
- WP-0.8: the chart of accounts is 15 accounts covering all five account types — the ones the two demonstration workflows post to plus what a trial balance needs to look like one. `FinanceAccounts` keeps the code constants (moved to `Features/ChartOfAccounts/`) and a fast test asserts every code it names, and every code the event seam posts to, exists in the chart. That closes the placeholder loop WP-0.5 opened
- WP-0.8: `Account.NormalBalance` is **derived from `AccountType`**, not stored. A column could disagree with the account's own kind and nothing would notice until a trial balance came out backwards
- WP-0.8: two tariffs ship, not one — residential inclining-block (the default) and commercial declining-block — so WP-2.3's rate engine has both shapes to get right, and so "the default plan" is visibly a property of a plan rather than of the system. A filtered unique index (`ux_rate_plans_default`) makes "exactly one default" a database fact

- WP-1.1: account numbers and location codes are **server-issued**, never caller-supplied: `C-000001` / `L-000001`, a fixed prefix and a zero-padded ordinal (`RegistryNumbers`). The padding is load-bearing — fixed-width numbers sort lexically in issue order, so the generator finds the highest issued with an `ORDER BY … DESC LIMIT 1` off the unique index, identically on Postgres and on the fast tier's SQLite, with no provider-specific SQL. A number of another shape (a legacy import) parses to no ordinal and cannot restart the series
- WP-1.1: issuing is behind `IRegistryNumberGenerator`, and `SequentialRegistryNumberGenerator` reads the highest committed number **inside the caller's transaction**. Two racing registrations both read it; the unique index rejects the loser and the service turns that into a 409 the caller can retry, so a duplicate account number is impossible rather than merely unlikely. A Postgres sequence would serialise the issue at the cost of SQL SQLite cannot run — and swapping to one is a DI change with no domain code touched
- WP-1.1: the account number is **fixed at registration** — `UpdateDetails` cannot change it. It is quoted on bills and referred to by every other module; correcting it would be a migration, not an edit
- WP-1.1: `Address` is an EF **owned type** on `ServiceLocation`, columns inlined (`address_line1`, `address_city`, …). - WP-1.2: **a service account is the pairing, and both ends are fixed at opening.** Changing who is served or where is a new account, not an edit — a meter, a bill and a work order all quote the account number, and moving either end would silently reattribute consumption that was already billed. Customer and location are plain Guid columns with real foreign keys but **no navigation properties**: the database still refuses an orphan account, while nothing invites a list query to walk into the customer and become a join it does not need
- WP-1.2: the lifecycle is `Pending → Active ⇄ Disconnected → Closed`, `Closed` terminal, in `ServiceAccountTransitions` beside WP-1.1's `CustomerTransitions`. **`Pending` has no route to `Disconnected`** — nothing was ever connected, so an account that never starts is closed rather than disconnected, otherwise "disconnected" stops meaning supply was cut. An illegal move is a 409 from the aggregate, and a fast test walks the graph to prove every declared status is reachable from `Pending` (a status nothing can reach is a pill, a filter and a report written for a state that never happens)
- WP-1.2: **one open account per premise is a database fact**, not a convention — `ux_service_accounts_open_location`, a unique index on `service_location_id` filtered `"status" <> 'Closed'`. The recommendation approved for this WP was to filter on Pending/Active; it is Closed-exclusive instead, because `Disconnected → Active` is a legal reconnection, so a disconnected account that did not hold its premise could be reconnected onto a premise somebody else had since been given. Closed is what releases a premise, which is also what makes reissuing one to the next occupant work. The service checks first so the loser of a race gets a 409 it can retry; a gate test inserts past that check and asserts Postgres answers `23505`
- WP-1.2: the index filter is a SQL string the compiler never reads, so **two fast tests hold it to the model** — one asserts it names `nameof(ServiceAccountStatus.Closed)`, the other that it names the column the status is actually stored in. Renaming either would leave the index quietly covering closed accounts, and only the demo would find out, by refusing to reissue a premise
- WP-1.2: **account history is a table of its own (`customers.service_account_history`), written by the aggregate, not by the service.** Every transition appends a line — including the opening one, whose `FromStatus` is null — so "the status moved and nothing says why" is unreachable rather than merely discouraged. It is deliberately *not* a replacement for the audit entry: the audit trail is the administrative record of a write, filtered by action in the platform schema, while this is the service record an agent reads back on the phone. Both are written in the same transaction, so neither can exist without the other
- WP-1.2: a history line captures the **actor's display name alongside their subject id** (`RegistryActor`), rather than resolving it against the identity provider when the history is read. A service record is read years later, by which time the person may no longer exist in the directory
- WP-1.2: **ids on the new entities are mapped `ValueGeneratedNever()`.** Not cosmetic: EF decides whether an untracked child of a tracked parent is an insert or an update by asking whether its key is set on a store-generated column, so with the Guid default a freshly appended history line is tracked as `Modified` and the save fails having updated nothing (`DbUpdateConcurrencyException`, 0 rows affected). Every id in GridCore is a Guid v7 minted in code from the clock; the mapping now says so. Any later entity whose children are added through a navigation owes the same line
- WP-1.2: opening an account requires the customer to be `Prospect` or `Active` and the premise to be active — both 409s naming what is in the way, since legality depends on current state. Opening **does not** move the customer's own status: a prospect becoming a customer is somebody's decision, and a cross-aggregate side effect here would move a status nobody asked to move. WP-2.x can consume `ServiceStarted` for that with no change in Customers

Stopped and Closed are separate facts on purpose: a disconnection stops consumption but leaves a balance and a premise allocated, where a closure is final — Billing's final-bill run and Metering's meter removal want different ones
- WP-1.2: `ServiceStartedAt` / `ServiceEndedAt` answer "since when is this live", and a reconnection **restamps the start and clears the end** rather than accumulating periods; the full sequence is the history's job. A fast test walks the graph and proves every declared status is reachable from `InStorage`
- WP-1.3: **status and condition are different kinds of thing and are two endpoints.** A status is a lifecycle and is guarded (an illegal move is a 409 from the aggregate); a condition is an *assessment* and is guarded by nothing — plant is repaired and plant weathers typhoons, so any grade may follow any other. One body carrying both would make "inspected, still in service" indistinguishable from a transition to itself

- WP-1.3: **the maintenance-history read model is one table, `assets.asset_history`, not two.** A technician in front of a transformer wants one timeline — installed, inspected Fair, repaired under WO-114, withdrawn — and splitting lifecycle from maintenance would mean interleaving two queries on screen to rebuild it. `AssetHistoryEntryType` tells the lines apart and `?entryType=` narrows the endpoint. - WP-1.3: maintenance cannot be booked against **retired** plant. The cost would land on a job nobody can go and look at
- WP-1.3: the manufacturer's **serial number is unique across the register**, on a plain unique index rather than a filtered one — both Postgres and SQLite treat NULLs in a unique index as distinct, so the poles and conductor spans that carry no serial are unaffected, and nothing here is a hand-written SQL predicate that can drift out of step with a column name (WP-1.2's lesson). Global rather than per-manufacturer: two vendors reusing one serial is possible in theory, but registering one physical transformer twice is the mistake that actually happens, and `(manufacturer, serial)` would let it through whenever a manufacturer is blank
- WP-1.3: an **install date in the future is refused**. A register records what exists; a future date is a typo, or a planned job — and a planned job is a work order, not an asset record
- WP-1.3: two events, not four — `AssetRegistered` and `AssetStatusChanged`, both through the outbox with **no consumer yet** (WP-1.1's precedent). One status event rather than one per verb, because the interesting fact is the pair: Work Orders cares that a transformer left service, Finance will care only about the move to `Retired`, and both read it off the same message. A **condition change publishes nothing** — it is this module's own assessment, revised at every inspection, where a status is the fact other modules gate on. Correcting details publishes nothing either: a fixed typo is not something a consumer acts on

Independent of the customer seeders — an asset attaches to no premise — and it walks each asset through the real transitions rather than assigning a status, so every seeded asset carries a genuine history and an illegal demo lifecycle fails in the seeder rather than shipping an unreachable state
- WP-1.4: **stock is a running total with an append-only ledger behind it, not a number.** `inventory.stock_levels` holds the quantity on hand per item per warehouse; every change goes through `inventory.stock_movements`, written by the aggregate so nothing outside it can move a quantity without the line that explains it (the guarantee `Asset` gives its history). `QuantityChange` is **signed** so summing the ledger reproduces the level with no lookup table of which types count as which direction, and `QuantityOnHandAfter` is stamped on every line so the ledger reads down the page — a total with nothing behind it is a number a storeman cannot argue with
- WP-1.4: **three movements, one table.** Receipt, Issue and Adjustment are one ledger with a type column rather than three tables, for the reason WP-1.3 gave for one asset history: the question is "what happened to this item", and splitting it would mean interleaving queries on screen to rebuild the answer. `?movementType=` narrows it — which is how WP-3.3 will read its issues and WP-4.1 its receipts
- WP-1.4: **an adjustment states the counted quantity and the difference is derived**, not a signed delta. That is what a stock take produces — somebody counted forty-two — and making the store do the subtraction is what stops "we are eight short" being entered as eight and going the wrong way
- WP-1.4: **an adjustment that agrees with the system is refused (409)**, which is the deliberate opposite of WP-1.3's re-assessment at the same condition being recorded. There the assessment *is* the record; here the ledger is for movements, and a zero line in a ledger read to explain a quantity is noise
- WP-1.4: **the reason on an adjustment is required, from both directions** — the validator answers 400 and `StockMovement.RequireReason` answers 400 for a seeder or a later module calling the service directly. Invariant 5 is the whole point of the endpoint: an adjustment moves stock with nothing physically moving, so an unexplained one is the write an auditor comes looking for
- WP-1.4: **the adjustment endpoint is the only one in the module gated above `inventory.write`** (`inventory.adjust`, held by Warehouse and Administrator only). A fast test asserts that it is the *only* one, rather than merely that it is gated: an adjustment quietly re-gated on write would leave the sensitive action to anyone with a receipt book. No new permissions — all three were declared and granted in WP-0.3
- WP-1.4: **the reorder level lives on the item-in-warehouse row, not on the item.** The main store and a crew depot do not want the same reorder level for the same connector. Zero means nobody has set one, so an empty shelf with no reorder level is *not* low stock — it is a line the store does not carry, and flagging every one of them is how a low-stock report becomes something nobody reads
- WP-1.4: **the low-stock rule exists twice on purpose** — `StockLevel.IsBelow` for the loaded aggregate and `StockLevel.BelowMinimum`, an `Expression`, for the `?belowMinimum=` filter, because EF cannot translate a call to the method. A fast test runs a table of cases through both (compiling the expression) so editing one without the other fails the loop, exactly as WP-1.2's tests hold its hand-written index filter to the model. At *or below*: a reorder level is the point you reorder at, not the point you have already gone past
- WP-1.4: the warehouse and low-stock filters **compose** rather than applying independently — "low stock in the north depot" has to mean low *there*, not "stocked there and low anywhere"
- WP-1.4: **quantity is `numeric(18,3)` and a finer one is refused, not rounded** — the same call WP-1.1 made for a deposit finer than a cent and WP-1.3 for a coordinate finer than six places, and for the same reason: the central rounding helper still has no home (WP-2.3 owns it) and the column would have truncated silently, leaving a count nobody chose and a ledger that no longer adds up to it
- WP-1.4: **`Each` is indivisible and a fractional quantity of it is refused.** Half a metre of conductor is a real quantity; half a connector is a broken connector, and a store that admits one has a count nobody can trust. `UnitsOfMeasure.IsDivisible` is the rule, beside the units rather than in whichever aggregate needed it first
- WP-1.4: **a receipt does not move the item's standard cost.** The catalogue line carries what one unit is reckoned to cost; the receipt records what *that* delivery cost on its own ledger line. Re-averaging with every delivery is a weighted-average valuation, which needs the rounding helper WP-2.3 owns and is Finance's decision rather than the store's
- WP-1.4: **the unit of measure is fixed once stock has moved (409).** Re-denominating 240 metres as 240 each would not convert the ledger behind it — it would silently reinterpret every line, and the store would be short by whatever the two units differ by. A genuine change of unit is a new catalogue line the old one is discontinued in favour of; before anything has moved it is still a correction
- WP-1.4: **catalogue codes are server-issued `ITM-000001`** (`RegistryNumberSeries`, three letters like `AST-` and for the same reason), and the manufacturer's part number is **unique when present** on an unfiltered unique index — NULLs are distinct on both Postgres and SQLite, so the cut conductor and the fixings by the kilo that carry no number are unaffected, and nothing here is a hand-written SQL predicate that can drift out of step with a column name. Global rather than per-manufacturer, on WP-1.3's reasoning: holding one part twice under two codes is the mistake that actually happens
- WP-1.4: **there is no DELETE here either**, and the deactivation asymmetry is deliberate on both axes: a **discontinued item** refuses receipts (buying more of a line you have stopped carrying is a purchase against the wrong item) but still allows issues, because the remaining stock has to be cleared off the shelf; a **closed warehouse** refuses receipts and reorder levels but allows issues and adjustments, or the stock on its shelves would be stranded until somebody reopened it
- WP-1.4: **no events, and `GoodsReceived` stays unraised.** It already exists in `Contracts` (WP-0.5) carrying `PurchaseOrderId` and `VendorId`, neither of which exists until WP-4.1 — bending it to a caller that is not there yet, or adding nullable ids to a Finance-facing event, would be worse than the wait. WP-4.1's receiving raises it and WP-3.3's issuance raises its own; the module already registers its context on the shared connection, so the outbox row will join the same transaction with nothing here to change. A catalogue line existing is not a fact another module acts on
- WP-1.4: **warehouses get a read endpoint and no write surface.** They are reference data shipped by migration (WP-0.8), so adding one is a migration — which is what keeps every deployment holding the same set (invariants 7 and 8). The list carries `LinesHeld` and `LinesBelowMinimum` so WP-1.5's screens do not have to fetch the whole catalogue to summarise a depot
- WP-1.4: **a write loads the levels and not the ledger.** A delivery of ten connectors must not have to read five years of movements to append a line to the end, so the movement is added to an unloaded collection and `Movements` is empty on a write path by design; the detail read includes both
- WP-1.4: **the warehouse is validated in the service, not the aggregate.** The aggregate's rules are about the item and the quantity, and a warehouse it cannot see is one it cannot get wrong — so `StockItem` takes a `Guid` while `StockItemService` loads the row (same schema, real foreign key) and answers 404 for an id that was never issued

- WP-2.2: **a meter carries its own register width, `Meter.RegisterDigits`, and rollover is computed from it.** "Consumption = current − previous with rollover handling" is unanswerable without knowing where the dials return to zero: the same pair of readings (99 850 → 120) is 270 units on a five-digit register and 900 270 on a six-digit one, and a test pins both. Deriving the width from `MeterType` was rejected as a fudge — two single-phase meters can carry different registers, and the width is transcribed off a nameplate like the serial number. It is this module's own table, so the column ships as a new migration (`WP22_Readings`), never an edit to the applied `WP21_Meters` (invariant 7)
- WP-2.2: **the backfill is five and then the default is dropped.** EF's own `AddColumn` backfill would leave zero, which is not a width any rollover arithmetic can run against — the first reading off such a meter would be refused rather than measured. The migration backfills to the ordinary domestic five and then `DROP DEFAULT`, so the column matches a model that declares no database default and the next `migrations add` has nothing to reconcile. A register width guessed by the schema is one nobody transcribed
- WP-2.2: **rollover is arithmetic, not an exception.** `ConsumptionCalculator` reports the units and a `RolledOver` flag; it does not try to tell a genuine wrap from a transposed digit, because from a pair of numbers the two are indistinguishable. `ReadingAssessment` is what notices the answer is implausible and raises a high-usage exception for somebody to look at. Two concerns, two classes, two reasons to change — a utility retunes what counts as high usage far more often than it changes what subtraction means
- WP-2.2: **a reading the register cannot display is refused, not folded into range.** 100 000 on a five-digit meter is a keystroke, and quietly reading it as 0 would turn one typo into a plausible-looking bill. Same call WP-1.1 made for a deposit finer than a cent, and WP-2.1 for an installation reading finer than three places — the central rounding helper still has no home (WP-2.3 owns it)
- WP-2.2: **exceptions are judged per day, never per reading period.** Reading periods are not equal lengths — a cycle slips, a meter is read late, a premise is re-read after a dispute — so a two-month gap would raise high usage on a household that used exactly what it always does. `HighUsageMultiple` is 3 and deliberately loose: this queue is worked by hand, and an exception nobody has time to clear is one nobody reads
- WP-2.2: **a missing read is a row, not an absent one.** `MeterReading.Reading` is nullable and null exactly when the code is `MissingRead`, with no consumption and no previous dials on the line. A cycle that could not read a meter is a real outcome and billing has to know it; dropping it from the batch would leave the utility unable to tell "used nothing" from "nobody went", and a bill would go out on stale dials. A missing read is also skipped when the *next* reading looks for what to measure from, or an unread month would report the following period's consumption as nothing and the one after as double
- WP-2.2: **a reading's baseline is two different questions answered from two different places.** The previous **dial** reading must come from *this meter on its current fitting* — dials do not carry over, so measuring an exchange meter from the old device's last reading would bill the difference between two unrelated registers. What the premise **normally uses** is the opposite: it belongs to the place, so the high-usage baseline is averaged across every recent reading at the premise, through exchanges. Keeping it per meter would blind the check for a whole cycle after every exchange — exactly when a wrongly fitted or mis-read meter is most likely. `ReadingBaseline.From` is pure and holds both rules, so all of it is provable with no database
- WP-2.2: **two queries per meter rather than one windowed query, and deliberately.** The previous dial reading is one side of every consumption figure and has to be exact, so it is fetched as itself; six consecutive missing reads would otherwise push it out of a window and quietly measure a period from the installation reading. The usage profile is an average and a six-row window is all it needs. Both are single index lookups and a route is capped at `MaxCycleSize` (500); if a real one outgrows that, the fix is a windowed query, not a longer transaction
- WP-2.2: **`IMeterReadingProvider` reads meters and never decides what a reading means.** Consumption, rollover and every exception code are the Metering module's work, computed from what came back — which is exactly what it will have to do with a real head-end that cannot be trusted to classify its own output. The interface and its DTOs live in `Contracts/Providers/` (the folder existed and was empty since WP-0.1); the simulator lives in `Modules/Metering/Simulation/` per ARCHITECTURE.md's module table, and is registered **only** against the Contracts interface, so nothing can resolve the concrete simulator and call it by name (invariant 6). A fast test asserts that
- WP-2.2: **the simulator carries its own PRNG (`DeterministicRandom`, SplitMix64) rather than using `Random(seed)`.** A seeded `Random` is only documented to be repeatable within one process on one runtime version, and the .NET team has changed the seeded algorithm before. The work package's requirement is that a seed reproduces a batch including its exceptions, so the sequence has to be part of GridCore rather than of whatever runtime it happens to run on. Twenty lines against a demo whose numbers move after a framework bump
- WP-2.2: **each meter draws from its own stream, keyed on the seed, the cycle code and the meter NUMBER.** Per-meter streams mean fitting a new meter somewhere does not shift everybody else's readings, and a test can pin one meter without pinning the route. And the **number, not the id**: Guid v7 carries random bits, so two freshly seeded demo databases hold the same meters under different ids, and keying on the id gave every machine a different demo world. That was caught by the seeder test, not by reasoning
- WP-2.2: **one reading per meter per cycle is a database fact — `ux_meter_readings_meter_cycle`, unfiltered.** A manual reading holds NULL in `cycle_code` and NULLs in a unique index are distinct on both providers, so a premise can be re-read by hand as often as a dispute needs while a cycle run twice collides instead of doubling every consumption figure it produced. The same trick as WP-2.1's `ux_meters_service_location`, and for the same reason: no SQL predicate naming a column for a later rename to desynchronise (WP-1.2's lesson)
- WP-2.2: **a cycle leaves ONE audit entry, and one event per reading.** Invariant 1 is about the write endpoint and a cycle run is one act — what an auditor asks is "who ran the August cycle and what came back", which one entry answers in a line, with the seed on it so the run can be reproduced. The readings are each already an immutable row stamped with who recorded them. No consumer yet (WP-1.1's precedent); WP-2.3 is the intended audience
- WP-2.2: **only a fitted meter can be read, and `Faulty` counts as fitted.** A meter suspected of running slow is still on the wall and is read on the next visit — which is often how the fault is proved. A meter in a store measures nothing, and reading one is a 409 rather than a 400: whether it could have produced a reading depends on where it is now, which no validator at the edge can see. A reading dated before the last one is refused for the same reason and with the same status

- WP-2.3: **a tariff's identity is its code AND its effective date, not its code.** WP-0.8 derived a rate plan's `ReferenceId` from the code alone and made `ux_rate_plans_code` unique on it, which made repricing structurally impossible — a second RES-STD would derive the same primary key. - WP-2.3: **the date that chooses the tariff is the end of the billed period, never today.** A run in September for August's consumption bills August's rates, whatever the tariff says by the time somebody presses the button — otherwise a late billing run silently reprices everything it touches and a re-run after clearing the exception worklist disagrees with the bills it ran beside
- WP-2.3: **three rate plan rows ship, not two, and both originals move back to 1 January 2025.** The residential tariff gains a revision effective 1 July 2026 so effective dating has two versions to choose between; WP-0.8's 1 January 2026 start fell *after* five of the twelve monthly cycles `MeterReadingsDemoSeeder` lays down, so those months priced to nothing at all — correctly (a premise metered before its tariff existed cannot be billed) and uselessly. Caught by the seeder test, not by reasoning
- WP-2.3: **`Platform/Monetary/Money.cs` is CONVENTIONS.md's central rounding helper, four work packages late.** Rounding is **half away from zero**, not `decimal.Round`'s default banker's rounding: the demonstrable rule beats the statistically neutral one wherever a person has to agree with the answer, and a customer checking by hand rounds 0.125 up. **Each bill line is rounded and the total is the sum of the printed lines** — rounding once at the end produces a document whose lines do not add up to its own total. The namespace is `Monetary`, not `Money`, because a type whose name matches its namespace is unreachable by simple name from anywhere under `GridCore.Platform`
- WP-2.3: **the helper does not license silent truncation.** WP-1.1's deposit, WP-1.3's coordinate, WP-1.4's quantity and WP-2.1's installation reading all still *refuse* a value finer than their column rather than rounding it, and those guards were deliberately left alone. Rounding is for figures GridCore computes; refusal is for figures somebody typed. `Money.IsRounded` is how a guard asks
- WP-2.3: **a bill equals the sum of its own printed lines, asserted in the aggregate.** Invariant 3 makes Finance throw when debits ≠ credits; `Bill.Calculate` is the same guard one step upstream, and it refuses rather than correcting — a total silently replaced by the sum of the lines would hide whatever produced the disagreement and the next bill would carry it too
- WP-2.3: **tier bounds are cumulative from zero, not per-tier allowances.** 600 kWh on the residential tariff is 500 units in tier 1 and 100 in tier 2, never 600 in each. That is the classic tiered-rate bug, and both sides of every shipped boundary are pinned in a table. **A tier that covers no units produces no line at all** — "0 kWh @ 0.1620 = 0.00" is noise on a document meant to be read — while the standing charge is always there, which is the difference between an empty house and one that is not connected
- WP-2.3: **Billing owns the account→tariff assignment and Customers is not touched** (owner's call). A `rate_plan_code` column on `customers.service_accounts` would put a billing concern in another module's schema and migrations. `billing.account_rate_plans` holds one row per account (`ux_account_rate_plans_account`), stores a **code and never a version id** — the point of effective dating is that a repricing reaches every account without anybody reassigning them — and **no row is an answer**: an unassigned account bills on the default, so a migrated database with no billing setup at all still produces correct bills
- WP-2.3: **two new cross-module read seams in `Contracts/Directories/`, shaped exactly like WP-2.1's `IServiceLocationDirectory`** (owner's call): `IServiceAccountDirectory` (Customers registers it) and `IMeterReadingDirectory` (Metering registers it). Billing consumes both and has never heard of a `customers` or `metering` schema. `FindOpenAtLocationsAsync` is the batched form of the derivation WP-2.1 named — "the account open at the premise this meter is on" — keyed by **premise**, because the caller holds a meter's premise and is asking who is served there
- WP-2.3: **a read seam rather than consuming `MeterReadingRecorded`.** WP-2.2 deliberately raised no "cycle finished, go and bill it" event because that would be an instruction rather than a fact. A billing run asks the register what a cycle produced, at the moment somebody decides to bill it — which is also what lets the run be re-run after the exception worklist has been cleared
- WP-2.3: **the seams are also what make the fast tier possible.** `FakeServiceAccountDirectory` and `FakeMeterReadingDirectory` stand in for two whole modules and their databases, so a billing run — the WP's headline behaviour — is unit-tested in milliseconds with no container. The real directories over real Postgres are proven once, in the gate tier
- WP-2.3: **a billing run produces DRAFTS and publishes nothing.** Issuing is the separate act that makes a bill money the utility is owed, and it is what publishes `BillIssued` for Finance to post the receivable against. A draft is a calculation, not a receivable — which is why `BillTransitions.IsOutstanding` excludes it
- WP-2.3: **a re-run skips what is already billed rather than refusing the whole run**, deliberately unlike WP-2.2's reading cycle, which answers 409. Re-running a billing cycle after clearing its exception worklist is ordinary work. `ux_bills_account_cycle` (unfiltered — an ad-hoc bill holds NULL in `cycle_code` and NULLs are distinct, WP-2.2's trick) is what actually prevents a duplicate; the pre-check turns the guarantee into a reason a billing officer can read
- WP-2.3: **a run reports what it did NOT bill, and why, in words.** A run that billed nine of twelve premises and said nothing about the other three is a run nobody can reconcile against the reading cycle. The reasons are on the single audit entry too. **A reading on the exception worklist is skipped** — billing a high-usage reading unseen is how a transposed digit reaches a customer as a demand for four thousand dollars — as is a premise with no open account (WP-2.1 seeds that case on purpose) and an account that was never energised
- WP-2.3: **ONE audit entry per run and per overdue review, one per bill issued or cancelled.** WP-2.2's call about a reading cycle: a run is one act and what an auditor asks is "who billed the August cycle and what came out of it". Issuing and cancelling are audited per bill because that is where the money starts and stops being owed
- WP-2.3: **`RegistryNumberSeries.NextManyAsync` is new, and load-bearing.** Rows added to a context but not yet saved are invisible to the query that issues the next number, so a run that asked once per bill would be handed `BIL-000001` every time and lose all but one to the unique index. The same reason a demo seeder assigns its own numbers (WP-1.1); stated once in Platform so the next module that writes a batch does not rediscover it
- WP-2.3: **the bill lifecycle is `Draft → Issued → PartiallyPaid ⇄ Overdue → Paid`, with `Cancelled` from anywhere unsettled**; `Paid` and `Cancelled` terminal. No `Overdue → Issued`: a bill does not stop having been late. `PartiallyPaid → PartiallyPaid` is deliberately **absent** — a self-transition is a way for a bill to "move" to where it already is — so `Bill.RecordPayment` handles a second instalment explicitly rather than consulting the machine. WP-2.4's `Adjusted` is not here
- WP-2.3: **`Bill.RecordPayment` is written now and called later.** WP-2.5 owns the payments simulator and the consumer that reduces a balance on `PaymentApproved`; what belongs in Billing is what it *means* for a bill to be paid, which is unit-tested here. The same shape WP-1.3 left `Asset.RecordMaintenance` in for WP-3.4. An overpayment is **refused**, not absorbed: a credit on the account is Finance's to hold (WP-2.6), and a bill that swallowed it would leave money with no record of where it went
- WP-2.3: **`Overdue` is reached by `POST /api/bills/overdue-review`, not by a scheduled job.** WP-0.4's scheduler exists and nothing is registered on it; a job that quietly moved bills overnight is a real feature with a real configuration screen behind it, and half of one here would be a setting nobody set. `Bill.MarkOverdue` returns **false** rather than throwing when a bill is not yet due — a review walks every outstanding bill and "this one is fine" is an ordinary answer
- WP-2.3: **everything a bill needs to be read is stamped on the bill** — the account number, the customer's name, the premise, the meter number, the dials either side, the tariff's code, name and effective date, the currency, and every line's own rate. Not denormalisation for speed: every one of those belongs to another module free to change it, and resolving them at read time would give a customer a different bill on a second look. WP-1.4's stamped quantity-on-hand and WP-2.2's stamped consumption, applied to the document a dispute is actually about
- WP-2.3: **no new permissions.** Reading is `billing.read`; the billing run, issuing, cancelling, the overdue review and the tariff assignment are all `billing.generate`, held by the Billing role and Administrator (WP-0.3). Setting the tariff an account bills on *is* part of running billing, and a permission of its own would be one nobody holds and one more thing to grant before the demo runs — the call WP-2.1 and WP-2.2 both made. `billing.adjust` is still claimed by nothing; WP-2.4 owns it
- WP-2.3: **there is no DELETE here either, and no write of any kind under `/api/rate-plans`.** A bill is a document the utility has to reproduce and defend years later; withdrawing one is a `Cancelled` status with a required reason. Tariffs are reference data, so publishing or repricing one is a migration and not a screen — a fast test asserts both
- WP-2.3: **`BillsDemoSeeder` (`billing.bills`, order 800) invents nothing.** Every bill goes through the real rate engine, the real selector and the real aggregate, and every transition is a real one — so an impossible demo figure fails at startup rather than shipping a number nothing explains. **Nothing is paid**: `PartiallyPaid` and `Paid` are reachable, but a payment invented here would be money with no record in Payments of where it came from, and WP-2.5 owns that
- WP-2.3: **no screens.** The work package is marked "unit, heavy" and names none; wiring a billing-run screen, a bill detail and the bill section of the 360° page belongs to the WP that gives somebody a reason to press them — exactly as WP-1.5 left the registry transitions as pills and WP-2.2 shipped no reading capture form. WP-2.7 owns the demonstration screen
- WP-2.4: **there is no `Adjusted` status** (owner's call, against `WORK_PACKAGES.md`'s "state transitions to Adjusted" and `SPEC.md`'s "Cancelled-Adjusted"). An adjustment is a financial correction, not a lifecycle state: the bill stays `Issued`, `PartiallyPaid` or `Overdue` and the correction is represented by immutable entries plus the audit trail. An `Adjusted` status would also have had to be outstanding, payable and reachable from three places, which is a fifth name for "still owed" rather than a new fact about the bill. **The two spec files still say otherwise and were deliberately not edited** — changing a spec is not this WP's to do. `BillStatus`/`BillTransitions` are untouched.
- WP-2.4: **a corrected bill still moves to `Paid` when a credit clears its balance.** Not the `Adjusted` state coming back in by another door: the utility is genuinely no longer owed anything, and leaving the bill `Issued` would park a zero-balance row on the AR worklist for good. `Bill.Adjust` goes through the same `Move` the machine guards, and `Issued`/`PartiallyPaid`/`Overdue → Paid` were all already legal. `AmountPaid` is **not** touched — settled by a credit is not the same as paid, and the ledger must not pretend money came in.
- WP-2.4: **an adjustment is a row in `billing.bill_adjustments`, never a bill line and never an edit to the total.** `Bill.TotalAmount` keeps saying what the rate engine produced and what the customer holds a copy of; the new `Bill.AmountDue` is that plus `Bill.AdjustmentTotal`, and `Balance` is now `AmountDue - AmountPaid`. An adjustment arriving as a line would have broken WP-2.3's money guard (total = sum of printed lines) or forced the total to move, which is the same thing twice. Migration `WP24_BillAdjustments`; index `ux_bill_adjustments_sequence`.
- WP-2.4: **`AdjustmentTotal` is a stored column, not a projection over the navigation** — a register list does not load a bill's adjustments, and a page reporting what was *printed* as what is *owed* would be wrong on every corrected bill. The cost is that the column can disagree with the history, so `Bill.Adjust` **refuses to run at all** unless the loaded entries sum to it (`BillService.LoadAsync` includes them). Same call, same reasoning as `Bill.Calculate` refusing a total that disagrees with its own lines.
- WP-2.4: **a kind and a positive amount, never a signed figure the caller types.** `Credit` and `Charge`; `BillAdjustment.Signed` applies the sign and refuses an enum value it does not know rather than defaulting to a direction. WP-1.4 made the same call about a stock take. The *stored* `Amount` is signed, so summing the history reproduces what is owed without a lookup table of which kinds count as which way.
- WP-2.4: **`Charge` is in scope, not only `Credit`.** "Authorized credits/corrections" runs both ways — a bill raised on a read that was too low leaves the customer owing the difference, and re-raising the whole document would give them two.
- WP-2.4: **a credit larger than the balance is refused (409), not absorbed**, and a `Draft`, `Paid` or `Cancelled` bill cannot be adjusted at all. Crediting past zero leaves money on the account, and a credit balance is Finance's to hold (WP-2.6) — word for word the call WP-2.3 made about an overpayment. A draft is not owed by anybody, so a wrong one is re-run or thrown away; money moving after settlement is a refund, which is Payments' act and Finance's entry.
- WP-2.4: **permission alone, no approval workflow** (owner's call). `POST /api/bills/{id}/adjustments` demands `billing.adjust`, which WP-0.3 gave the Billing role, Managers and Administrator — and gave Managers **without** `billing.generate`, so this is a genuinely different gate rather than a tidier name for the run permission. A fast test asserts it is the *only* route behind `billing.adjust`, the shape WP-1.4 used for `inventory.adjust`. `ApprovalQueueDemoSeeder`'s pending `billing.adjustment` request stays decorative until WP-4.4 wires the inbox.
- WP-2.4: **`BillAdjusted` is published through the outbox now** (owner's call), unlike WP-2.3's deliberate silence on cancellation. The difference is that an adjustment states a **signed change to a known amount**, which WP-2.6 can post as a second balanced entry without guessing what was meant — invariant 3's "corrections are new entries, never edits" reaching across the module boundary. Nothing consumes it yet; the gate-tier test proves the outbox row is staged inside the same transaction as the entry and the audit row.
- WP-2.4: **audited against the bill, not against the entry**, reusing `AuditEntityTypes.Bill` with the new `AuditActions.BillAdjusted` (`bill.adjust`). What an auditor asks is "what did this change about what the customer owes", which the entry alone cannot answer; `BillSnapshot` gained `AdjustmentTotal` and `AmountDue` so the before/after shows the money moving while `TotalAmount` visibly does not.
- WP-2.4: **`BillsDemoSeeder` now corrects two bills, one each way**, through the real `Bill.Adjust` — a proportion of the balance rather than a fixed figure, so the correction cannot outgrow the bill however the seeded consumption moves. Two different bills rather than two entries on one: a credit and a charge cancelling out would show a history and an unchanged amount owed, which is the one arrangement that teaches a reviewer nothing. A demo world with fewer than two outstanding bills seeds none and does not throw.
- WP-2.4: **no screens.** The WP names none, and `/billing` is still a `ModulePlaceholder`. `BillResponse` carries `adjustmentTotal`, `amountDue` and the `adjustments` array ready for the WP that builds the screen.
- WP-2.5: **a payment is always taken against a bill, and the bill's balance is pre-checked before the provider is asked** (owner's call, from the two ambiguities raised at kickoff). `Payment.Take` refuses an amount larger than `bill.Balance` with a 409, so the utility never authorises money the bill cannot accept — `Bill.RecordPayment` refuses an overpayment outright, and the alternative (absorbing the difference) would leave a credit with no record of where it went. It is a pre-check, not a lock: if the balance moves in between, the consumer's `RecordPayment` refuses and the message faults, rather than a bill going negative. **Account-level payments are out of scope** — `PaymentApproved.BillId` stays nullable and the consumer ignores a null, so the later WP that takes one has its seam already.
- WP-2.5: **`Refunded` is an outcome the seam carries and nothing more** (owner's call). It is declared on `PaymentOutcome` because `WORK_PACKAGES.md` names it and because widening the set later would mean revisiting every consumer that switches over it, but `AuthorizeAsync` is only ever asked to take money and a fast test asserts the sandbox never answers a charge with it. **`payments.refund` still opens no route** — a refund needs a ledger to post the reversal into and Finance's does not exist until WP-2.6 — and a fast test asserts the permission is unclaimed, the shape WP-2.3 used for `billing.adjust`.
- WP-2.5: **`IPaymentProvider` is GridCore's second provider interface and copies `IMeterReadingProvider` exactly.** The sandbox lives in `src/Modules/Payments/Simulation/` and is registered **only** against the Contracts interface (a fast test asserts the concrete type is not resolvable), so production swaps a real gateway in by changing one DI line. A provider **charges an instrument and reports what happened**; it never decides what its own answer means. `IVendorProvider` (WP-4.1) and `ICrewProvider` (WP-3.2) are the remaining two.
- WP-2.5: **`DeterministicRandom` moved from `Modules/Metering/Simulation/` to `Platform/Simulation/`.** The payment sandbox is its second caller and the vendor and crew simulators will be the third and fourth; two byte-identical copies of a PRNG are two sequences one framework bump apart from disagreeing. Strictly this touches another module, so it is flagged rather than buried: the change is a namespace, Metering's own tests are unchanged apart from an import, and `DeterministicRandomTests` moved to `Platform.UnitTests` with the type. STATUS.md's "copy this shape" note meant the **keying discipline** — key on the number, never the id — which the sandbox does follow.
- WP-2.5: **the sandbox keys its stream on the payment NUMBER, and pins outcomes to instrument suffixes.** Same seed, same answer, on every machine — a demonstration whose declines moved per database could not be rehearsed. A refused payment is retried as a **new attempt with a new number**, so it draws a new stream and may well be approved, which is what a customer trying a second card actually experiences. Instruments ending `0002`/`9995`/`0000` always produce Declined/InsufficientFunds/Timeout, the way every real sandbox works, so a demo can show a refusal on purpose instead of taking payments until one happens. **Cash is never refused** — the money is already in the drawer.
- WP-2.5: **an outcome is not a status.** The provider's verbatim answer is stored beside a shorter lifecycle: `Declined` and `InsufficientFunds` both leave the payment `Declined` (no money moved either way; what a screen renders differently is the reason), while **`Timeout` leaves it `Failed`, never `Declined`** — the money may have moved and the answer been lost, so it must never be folded in with the refusals and retried blindly. An outcome this module does not know is refused rather than defaulted, the call `BillAdjustment.Signed` makes about an unknown kind.
- WP-2.5: **a refusal is a 200 with a recorded row, not a 4xx.** The provider declining is an answer, not a failed request: the attempt is stored, audited and returned with `approved: false`. A 4xx would be a 4xx with a committed row behind it, which is the one response nobody can act on. The genuine 4xx paths are the ones that record nothing — no such bill (404), a bill nobody owes (409), more than is outstanding (409), a figure finer than a cent or a method the utility does not accept (400).
- WP-2.5: **every attempt is audited, refusals included** (`AuditActions.PaymentTaken`, `AuditEntityTypes.Payment`). A run of declines on one account is exactly what somebody comes looking for, and a trail holding only the successes could not answer them. **The instrument is deliberately absent from the snapshot** — it is on the payment because a clerk needs to say which card was used, and the audit trail is read far more widely.
- WP-2.5: **Billing gains its first consumer, and it is the only thing that reduces a balance.** `PaymentApprovedConsumer` (dedupe name `billing.payment-approved`, distinct from `finance.payment-approved` — two modules claim the same event independently and a shared name would mean whichever ran first silently suppressed the other) calls the `Bill.RecordPayment` WP-2.3 left with no caller. There is deliberately **no endpoint** for it: money arriving is Payments' fact to state, and a route here would be a second way to mark a bill paid with no payment record behind it. It publishes nothing — Finance already heard the same fact from Payments.
- WP-2.5: **the fourth cross-module read seam, `IBillDirectory` (`Contracts/Directories/`), registered by Billing.** Payments checks a balance through it and has never heard of a `billing` schema. **The seam computes `Balance` rather than handing over three columns and a sign convention** — since WP-2.4 what is owed is the printed total plus every correction, less what has been paid, and a caller given the parts is one refactor away from checking a payment against the wrong figure. Read-only, like every other directory: writing to a bill stays behind `IBillService`.
- WP-2.5: **the provider is called inside the write transaction, deliberately.** The alternative is charging a customer and then failing to record it, which is money with no row. The sandbox answers in microseconds; a real gateway would want the payment committed as `Pending` first and settled by callback, which is a real integration with a real reconciliation job behind it. Noted rather than built.
- WP-2.5: **`BillPayments.ApplyAsync` is free of MassTransit types** so the whole consume path is exercised in the fast tier — the real `IdempotentEventHandler`, the real dedupe store, the real unit of work — with `PaymentApprovedConsumer` as the four-line adapter the platform already documents as the untestable part.
- WP-2.5: **no demo seeder** (against STATUS.md's WP-2.3 note that WP-2.5 would pay the demo bills). A seeded payment either publishes `PaymentApproved` — making the demo world's bills depend on broker timing, which no other seeder does — or does not publish, and leaves settled payments beside bills that still say they are owed. Neither reconciles. WP-2.7's end-to-end walk of the revenue cycle is where paid bills belong.
- WP-2.5: **no screens.** The WP names none and there is no `/payments` nav destination; `/billing` is still a `ModulePlaceholder` labelled WP-2.3. WP-2.7 owns the demonstration screen.
- WP-2.6: **Finance consumes `BillAdjusted` and posts a second balanced entry** (owner's call, from the kickoff ambiguities). `WORK_PACKAGES.md`'s WP-2.6 text names only `BillIssued` and `PaymentApproved`, but WP-2.4 published the correction as a **signed change to a known amount** precisely so the ledger could post it without rewriting anything — and without a consumer, AR would diverge from Billing the first time a disputed bill was credited. A credit (`Amount < 0`) debits revenue and credits receivables, the exact reverse of issuing; a charge posts the same way round as issuing. **The magnitude goes on the correct side rather than a negative amount on the original side:** a negative debit and a credit are the same money, and only one of them can be added up by eye. `BillAdjustedConsumer`, dedupe name `finance.bill-adjusted`.
- WP-2.6: **`JournalPostingIntent` and the journal entry carry `ServiceAccountId`/`CustomerId`** (owner's call). Without a party dimension the ledger can say what the utility is owed but not by whom, and Finance may not ask Billing — so the AR view is the receivables control account's own lines grouped by the party stamped on their entry. **On the entry, not the line:** every posting GridCore makes concerns one party at most, and a party per line would permit a batch entry naming two customers, which nothing raises and nobody could reconcile. A goods receipt carries neither — its subsidiary is a vendor, and that ledger is WP-4.1's.
- WP-2.6: **a journal line holds a foreign key to the chart row, not a stamped account code** — the deliberate opposite of every other cross-reference in the codebase. A bill stamps its tariff's rate and a payment stamps the customer's name because the thing referred to lives in another module and will move; the chart is reference data in *this* schema whose code is its identity and never changes. So "you cannot post to an account that does not exist" is a database fact, and there is no second copy of the code to disagree with the first. This is the lookup WP-0.8 recorded as owed.
- WP-2.6: **the ledger is append-only in code**, guarded in `FinanceDbContext.SaveChanges(Async)` for both `JournalEntry` and `JournalLine` — invariant 3, in the shape WP-0.4 gave the audit trail. Lines are covered as well as entries because an entry balances exactly as long as nobody has edited the lines under it. The chart of accounts is deliberately **not** covered: it is reference data and a migration is how an account is meant to be corrected.
- WP-2.6: **balanced-or-throw is asserted twice** — once in `JournalPostingIntent.For` (which also now refuses a two-sided line, a negative amount and an amount finer than a cent) and again in `JournalEntry.Post`. The second is unreachable through the first, which is the point: CONVENTIONS.md asks for the assertion at the posting, and an invariant this expensive to discover late is worth two cheap guards. **A sub-cent amount is refused, not rounded** — the amounts arriving were computed and rounded upstream, so one finer than a cent means an upstream total that no longer adds up, and rounding here would hide exactly that.
- WP-2.6: **`ux_journal_entries_event` — one entry per event, as a database fact.** The dedupe claim already stops a redelivery reaching the ledger and commits in the same transaction as the entry, so this should never fire; it exists because "should never" is doing a lot of work in a sentence about money (a consumer renamed, a claim table restored from an older backup). Unfiltered, so a manual entry holding NULL stays possible — WP-2.3's `ux_bills_account_cycle` trick.
- WP-2.6: **the accounting date is the event's `OccurredAt`, not the clock**, so a redelivery replayed a week later posts to the day the bill was issued rather than moving last month's revenue into this month. `PostedAt` records when Finance actually wrote it; both are stored.
- WP-2.6: **the trial balance lists every account in the chart, including the untouched ones**, and nothing anywhere stores a balance. An account's balance is the sum of its lines, computed on demand — the call `Account.NormalBalance` already made, applied to money. A report that showed only accounts with activity would change shape as the demo ran and would not let a reader tell an untouched account from a missing one. `Balance` is signed by the account's normal side, so an ordinary month is all positives.
- WP-2.6: **the read surface is read-only and that is structural, not an omission.** `/api/finance/accounts`, `/journal-entries`, `/journal-entries/{id}`, `/trial-balance` and `/accounts-receivable`, all gated on the pre-existing `finance.read`; a fast test asserts the module maps **no HTTP verb but GET**. **`finance.post` stays claimed by nothing** (owner's call) — SPEC.md does not ask for a manual journal, and a ledger whose only author is the event seam cannot disagree with the modules upstream of it. **No refund either:** WP-2.5 left `payments.refund` unclaimed because a refund needs a ledger to post the reversal into, and building that ledger is not the same act as performing one. Fast tests assert both permissions are still unclaimed.
- WP-2.6: **no demo seeder** (owner's call), for a sharper reason than WP-2.5's. `BillsDemoSeeder` writes bills straight to Billing's tables and publishes nothing — a seeder adds entities and never publishes — so the ledger has no events behind it to post. Inventing matching entries would put figures in a trial balance that no upstream fact explains, which is the one thing a ledger must never do. **The demo world therefore opens with an empty ledger and a zeroed trial balance**; WP-2.7's end-to-end walk raises real events and the ledger fills itself from them.
- WP-2.6: **`RecordingJournalPostingSeam` in the gate tier now decorates the real ledger rather than replacing it**, so a test can still await the seam firing *and* read back the entry it caused. Its signal fires inside the consumer's transaction, so a test that wants the committed row polls the table rather than awaiting the recorder. **`GateFixture.ResetAsync` retries a Postgres deadlock (up to five attempts, no fixed pause):** a reset now races a real background writer, because a consumer posting a journal entry takes locks on the rows Respawn is deleting. That is what a ledger written by consumers does, not flakiness to paper over.
- WP-2.6: **no screens.** The WP names none; WP-4.2 owns the Finance views (AR/AP/journal/trial balance) and `/finance` is still a `ModulePlaceholder`. The API is shaped so those screens are a client, not a rewrite.
- WP-2.7: **the demonstration screen lives at `/billing`** (owner's call), not at a new nav destination. DESIGN.md's sidebar is the reference screenshot's and adding a "Workflows" area to it would be a DESIGN.md change dressed up as a screen. Billing & Payments is where somebody looking for "raise a bill and take the money" goes, and the walk *is* that. Its `owners` label — stale at `WP-2.3` ever since that work package shipped no screens — is gone with the placeholder, and `registryPages` in `web/src/routes/routes.tsx` was renamed **`builtPages`**: the map now holds a workflow screen and had no business being named after the other kind.
- WP-2.7: **the wizard fills the ledger; no seeder does** (owner's call, confirming WP-2.5's and WP-2.6's deferrals). Seeders stay non-publishing, so a freshly seeded demo world still opens on an empty general ledger and a zeroed trial balance — that is the correct answer, because `BillsDemoSeeder` writes bills without publishing and no upstream fact explains any entry. Walking the screen raises real `BillIssued` and `PaymentApproved` events through the outbox, and Finance's consumers post from those. **A demonstration therefore has to be walked before the books say anything**, which is the honest version of the alternative.
- WP-2.7: **the E2E test lives in `tests/IntegrationTests`, not a new project** (owner's call), and is **not a new xUnit collection**. A second `ICollectionFixture<GateFixture>` would start a second Postgres, RabbitMQ and Redis for the sake of a naming distinction — the per-class-container mistake CONVENTIONS.md rule D exists to prevent. So `E2E/RevenueCycleTests` joins `GateCollection` and carries a second trait, **`Tier=E2E`**, which `--filter "Tier=E2E"` selects on. `Category=Integration` deliberately keeps its existing value rather than gaining a second: a new value on that key would have to be excluded by name in every fast-loop command in the repository.
- WP-2.7: **the E2E pins the simulator's stream instead of drawing a fresh one.** The reading simulator keys each meter on (seed, cycle code, meter *number*) and roughly one stream in ten answers with a missing read or unchanged dials — both of which the billing run correctly refuses to bill. A random cycle code therefore failed the walk about one run in ten on a step working exactly as designed, and it did: the first full gate run after the test was written. The code is fixed per walk (`E2E-revenue`, `E2E-refusal`), the seed is `4471` and the serial is fixed, so a Respawn reset leaves `metering.meters` empty and the number series hands out the same meter number every time. **Reusing a cycle code across resets is safe** precisely because the reset truncates the readings and bills the two unique indexes guard.
- WP-2.7: **a billing run that raised nothing fails with the run's own reasons**, not with "the collection was empty". `BillFor` quotes `SkippedReading.Reason` for every meter passed over. A run says in words why it did not bill a reading, and that sentence is the most useful thing it produces — an assertion that discarded it would turn a five-second diagnosis into an afternoon.
- WP-2.7: **the walk drives module services, not HTTP.** The endpoints, their policies and their ProblemDetails are asserted in the fast tier where they cost milliseconds; what needs containers is the seams underneath, and a service call reaches every one of them. This is the shape the rest of the gate tier already uses (`PaymentRegistryTests`, `GeneralLedgerTests`).
- WP-2.7: **each step of the E2E asserts its own downstream effect, in place, rather than the walk asserting the ledger at the end.** The receivable is raised by *issuing* the bill and the cash entry by *approving* the payment, so the charge is asserted immediately after issuing and before a payment is taken — a test that looked only once, at the finish, could not say which step had posted what, and would pass just as happily if one step had done both.
- WP-2.7: **the reading step runs a real cycle over the whole estate**, and the screen says so. There is no per-meter form of a reading run and inventing one for a demonstration would demonstrate a different product; the cycle is also the only path through `IMeterReadingProvider`, which is the boundary WP-2.2 built and the thing a demonstration most needs to show. **Consequence, accepted:** each walk raises drafts for every other billable premise in the cycle too, and those drafts accumulate (a draft is owed by nobody, so they are harmless, and only the walk's own bill is issued). A screen that cancels or cleans them up belongs to whichever WP gives somebody a reason to press it.
- WP-2.7: **the wizard's steps map SPEC.md's nine acts onto seven cards**, because two of the nine are not buttons. Consumption is what Metering works out the moment a reading lands — a provider reads meters and never decides what a reading means — and updating a balance happens in Billing's schema because Payments published a fact. A wizard with a "Calculate consumption" button would be teaching the reader something false about the architecture. Each card names the SPEC steps it covers, and a fast test asserts all nine are covered exactly once.
- WP-2.7: **"the numbers reconcile" is three figures, not a slogan.** `reconcile()` is pure and compares what the billing register says (`amountDue`, `amountPaid`, `balance`) with what the ledger says, read back through the receivables view — plus the trial balance's own `isBalanced`. Finance was told none of them: it heard two events and posted from those alone, so agreement is two modules arriving at the same answer rather than one copying the other's total. **Compared in cents**, never with `===`: these are `decimal` on the wire and `number` after `JSON.parse`, and 0.1 + 0.2 is a poor reason to tell somebody their ledger is wrong.
- WP-2.7: **a refused payment carries the walk on to the books rather than ending it.** The payment step is complete whether the provider approved or refused, because a refusal is an answer — and what the books then say is that the customer still owes the money, which is the more instructive half of the demonstration. Both the E2E and the page test assert the refusal propagates nowhere: nothing published, the bill still `Issued`, receivables still carrying the debt, and the trial balance still balanced, because a debt is as balanced an entry as a settlement.
- WP-2.7: **the accounting step waits and reads; it never posts.** It polls the journal until every posting the walk should have caused has arrived — `BillIssued` always, `PaymentApproved` only if the provider approved, since waiting for a cash entry that will never come would hang the walk on a step that is already correctly finished. Nothing on this screen can write to the ledger, which is WP-2.6's read-only surface holding at the UI.
- WP-2.7: **this is GridCore's first screen that writes**, so the react-hook-form + zod + shared-toast shape CONVENTIONS.md asks for starts here; WP-1.5's registries are read-only by design. New module clients: `api/billing.ts`, `api/payments.ts`, `api/finance.ts`, plus writes on the customers and metering clients. Only what the walk needs is in them — **WP-4.2 extends `api/finance.ts` rather than replacing it.**
- WP-2.7: **the payment step waits for Billing's consumer before reporting the balance.** Taking a payment returns before the broker has carried `PaymentApproved` anywhere, so the step re-reads the bill until `amountPaid` moves — polling, which returns the instant the consumer commits, never a fixed sleep. **A timeout returns the unmoved bill rather than throwing:** the payment succeeded and the fact is in the outbox, and telling somebody their money vanished because a broker was slow would be a lie. The screen says so in those words.
- WP-2.7: **`SPEC.md` and `WORK_PACKAGES.md` no longer say bills reach an `Adjusted` state** (owner's call, closing the reconciliation WP-2.4 deliberately left open). WP-2.4 decided before any code was written that an adjustment is a financial correction rather than a lifecycle move; both spec files still described the old shape, and a spec that disagrees with the code is worse than either. The lifecycle in SPEC.md now reads `Draft/Issued/PartiallyPaid/Overdue/Paid/Cancelled` and adjustments are described as immutable entries plus an audit trail. **No code changed** — the code was already right.
- WP-2.7 (fix): **enums cross the wire as names in BOTH directions** — `GridCoreJson` (`src/Platform/Serialization/`), registered by `builder.Services.AddGridCoreJson()` in `Web.Host/Program.cs` beside `AddProblemDetails` because it is the same kind of decision: what every module's HTTP surface looks like from outside. Every response DTO already hand-stringified its enums so a client renders a word rather than an ordinal, but **nothing configured the reading half**, so `{"class":"Residential"}` was refused with `400 Failed to read CreateCustomerRequest` while the response for that same field came back naming one. An API that will not accept what it emits is a bug in the API, not in its callers. **Safe host-wide because no response record on any module's HTTP surface exposes a raw enum** — they all stringify by hand — so the converter has no output to alter; and `JsonStringEnumConverter` still reads integers, so anything already posting ordinals keeps working.
- WP-2.7 (fix): **the gap that let it through was that no test had ever crossed JSON in the reading direction.** Every write in every tier went through a module service or built the request record in C#: the fast tier asserts endpoint *metadata*, the gate tier's only HTTP client is anonymous (WP-0.3's security is real OIDC, so an authenticated test client does not exist), and the E2E drives services. The regression is therefore fast-tier and DTO-level: `RegistryRequestBindingTests`, `MeterRequestBindingTests`, `BillRequestBindingTests` and `PaymentRequestBindingTests` deserialize the **literal payloads the SPA sends**, because a DTO constructed in C# proves the shape compiles and proves nothing about what the host can read. **A module adding an enum-bearing request DTO owes one of these.**
- WP-2.7 (fix): **an unrecognised enum name is refused, never defaulted**, and each binding test pins that as a failure path against its own zero member. The zero members are the dangerous ones: `CustomerClass.Residential`, `MeterType.SinglePhase` and above all `BillAdjustmentKind.Credit` — a value quietly defaulted there would turn a charge into a credit and take money off a bill with nothing to say it had happened.
- WP-2.7 (fix): **the shell's scrolling column is `relative`, and that class is load-bearing.** `.sr-only` is `position: absolute` with no offsets, and an absolutely positioned box whose ancestors are all static gets the **initial** containing block — so it is not clipped by `AppShell`'s `overflow-hidden` (overflow only clips descendants whose containing-block chain runs through that element) and it contributes to the **document's** scrollable height at its own unscrolled flow position. On a page taller than the viewport that reads as a browser scrollbar and a band of blank white below the shell. The revenue-cycle walk was the first page tall enough to show it: every step card carries an `.sr-only` label and the last sits far below the fold. Positioning the column makes it the containing block, so those boxes scroll with the pane they belong to. **Pre-existing trap, not a new one** — `DataTable`'s `<caption className="sr-only">` had the same exposure on any page long enough. `position: relative` does not affect `fixed` descendants, so the drawer and the mobile nav overlay are untouched.
- WP-2.7 (fix): **`Select` gained `fullWidth`.** The wrapper is what the chevron is positioned against, so the wrapper decides the control's width — left `inline-flex` it shrink-wraps, and a `w-full` on the `<select>` inside resolves against a parent that has already sized to the select's own longest option. The three form selects on the demonstration screen were rendering narrower than the inputs beside them. Filters and card headers keep the shrink-to-fit default, which is what they want.
- WP-2.7 (fix): **the layout regressions are class-level assertions and say so.** jsdom does no layout — there are no boxes to measure and `scrollHeight` is always zero — so `app-shell.test.tsx` and `select.test.tsx` assert the classes that produce the behaviour, with the mechanism written down beside them. That is weaker than a real layout test and it is what this tier can honestly do; a browser-based check would catch the class of bug rather than the one instance, and belongs with the authenticated end-to-end gap already noted.
- Phase 2.5 (planning): **Customers is deepened before Billing.** The Revenue Cycle proved the pipes end to end, but Customers is still the Phase 1 spine (records, locations, accounts, states) — so a billing-deepening pass would have had to invent the customer surface it needs (intake, search, 360, deposits, transitions) as a side effect of billing work. Building the CSR desk first gives that pass something to land on, and every Phase 2.5 WP records whether it touches Billing so the map is already drawn. Sequenced registration → search → 360 → the CSR interactions (contacts, deposits, notes, documents, transitions); new gate `v0.3.5-customers` between `v0.3-revenue` and Phase 3. Numbered WP-2.8…WP-2.15 rather than WP-2.5.x — `WP-2.5` is already the payments simulator and the branch names would collide.
- Phase 2.5 (planning): **customer self-service portal and external customer login stay deferred.** Phase 2.5 is entirely internal/CSR-side, behind the existing 8-role RBAC; nothing in it is customer-facing. A portal is a second authentication surface with its own identity model, registration, and public exposure — a project in its own right, not a feature of the Customers module. Note that `SPEC.md`'s "Deferred beyond MVP" list does not currently name it; this line is the record until a WP says otherwise.
