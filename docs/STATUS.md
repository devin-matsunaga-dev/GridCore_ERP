Copy `src/Modules/Assets` for a *smaller* complete module than Customers: one slice, one aggregate, a history table and a seeder.
- **An asset attaches to no service location, and that is deliberate** — cross-module rows are unreachable, and most plant does not stand at a premise anyway. Where an asset is, is `GeoPosition` (two `numeric(9,6)` columns, `Position` computed from them) plus a free-text `LocationNote`. **Do not add a `ServiceLocationId`** in WP-1.5 or WP-3.x; resolve a premise through Customers' service if a screen needs one.
- **`GeoPosition` is a struct and is NOT an EF owned type.** EF does not map an owned struct at all, and an owned class with two required properties cannot be an optional dependent in a shared table. The columns are mapped directly and `builder.Ignore(asset => asset.Position)` keeps the computed property out of the model — a get-only property with no backing field is otherwise an EF model error. Any later value object of this shape owes the same treatment.
- **One history table, `assets.asset_history`, is the maintenance-history read model.** `AssetHistoryEntryType` is `Registered`/`StatusChanged`/`ConditionAssessed`/`Maintenance`; the first three are written by the aggregate today. **WP-3.4 calls `Asset.RecordMaintenance(workOrderId, summary, actor, now)`** from its work-order consumer — the writer already exists and is unit-tested, only the caller is missing. `WorkOrderId` is a plain Guid with no FK.
- **Status is guarded, condition is not.** `InStorage → InService ⇄ UnderMaintenance → Retired` (`Retired` terminal, no `InStorage → UnderMaintenance`) in `AssetTransitions`; an illegal move is a **409 from the aggregate**. A condition is an assessment — any grade may follow any other, including the same grade again, which is recorded on purpose. Two endpoints: `POST /{id}/status` and `POST /{id}/condition`.
- Serial numbers are **globally unique on a plain unique index** (NULLs are distinct on both providers, so poles and spans are unaffected). No filtered-index SQL string this time — WP-1.2's two guard tests exist because that string is SQL the compiler never reads.
- Two events through the outbox, still **no consumer**: `AssetRegistered`, `AssetStatusChanged`. A condition change and a details correction publish **nothing**, deliberately.
- **The Customers module is complete for Phase 1 (WP-1.1 + WP-1.2)** — `customers.customers`, `customers.service_locations`, `customers.service_accounts` and `customers.service_account_history`; migrations `WP11_Customers` and `WP12_ServiceAccounts`; endpoints under `/api/customers`, `/api/service-locations` and `/api/service-accounts`, all gated on `customers.read` / `customers.write` (still no new permissions; only Administrator and CustomerService hold write). **WP-1.3 onwards is a different module** — copy `src/Modules/Customers` for the complete example.
- **A service account is the pairing, and both ends are fixed at opening.** Changing who is served or where is a new account: a meter, a bill and a work order all quote the account number. Customer and location are plain Guid columns with **real foreign keys but no navigation properties** — the database refuses an orphan, and nothing invites a list query to become a join. WP-2.1's meter attaches to the *account*, not to the customer.
- **The account lifecycle is `Pending → Active ⇄ Disconnected → Closed`**, `Closed` terminal, in `ServiceAccountTransitions`. `Pending` has **no** route to `Disconnected` — an account that never started is closed, or "disconnected" stops meaning supply was cut. Start/stop/close are POST sub-resources (`/start`, `/stop`, `/close`), never a status PUT, and an illegal move is a **409 from the aggregate**.
- **One open account per premise is a database fact** — `ux_service_accounts_open_location`, unique on `service_location_id` filtered `"status" <> 'Closed'`. Closed-exclusive rather than Pending/Active-only, because a disconnected account is reconnectable and must keep holding its premise. Closing is what frees a premise for the next occupant. Two fast tests hold the filter string to `nameof(ServiceAccountStatus.Closed)` and to the stored column name — it is SQL the compiler never reads. A gate test inserts past the service's own check and asserts Postgres answers `23505`.
- **Account history is its own table, written by the aggregate.** Every transition appends a line (the opening one has a null `FromStatus`), so a status cannot move without a record of why. It is **not** the audit trail: the audit entry is the administrative record of a write, this is the service record an agent reads back on the phone. Both commit in the same transaction. The actor's display name is captured *alongside* their subject id (`RegistryActor`), because a history read years later outlives directory entries.
- **⚠️ New entity ids are mapped `ValueGeneratedNever()` and that is load-bearing.** EF decides whether an untracked child of a tracked parent is an insert or an update by asking whether its key is set on a store-generated column — leave the Guid default and a freshly appended child is tracked as `Modified`, so the save throws `DbUpdateConcurrencyException` ("expected 1 row, affected 0"). Any later entity whose children are added through a navigation collection owes the same line. Cost half an hour in WP-1.2.
- Opening an account requires the customer to be `Prospect` or `Active` and the premise active — both 409s. Opening deliberately **does not** move the customer's own status; WP-2.x can consume `ServiceStarted` for that with no change here.
- Four new events through the outbox, still **no consumer** (owner's call): `ServiceAccountOpened`, `ServiceStarted`, `ServiceStopped`, `ServiceAccountClosed`. Stopped and Closed are separate facts — a disconnection leaves a balance and a premise allocated, a closure is final.
- `ServiceStartedAt` / `ServiceEndedAt` answer "since when is this live"; a reconnection restamps the start and clears the end rather than accumulating periods — the sequence is the history's job.
- **Two demo seeders in Customers now:** `customers.registry` (200) and `customers.service-accounts` (300). Two SQLite gotchas it works around: no `jsonb` (the context relaxes the column type off Npgsql) and **no `ORDER BY` on `DateTimeOffset`** (order by the Guid v7 key instead, which sorts chronologically on both providers).
- New entities use `Guid.CreateVersion7(now)` so the PK index orders chronologically. Entries created in the *same* clock instant have no defined order — a test with a frozen `FakeClock` must advance it between writes.
- **Cross-context atomicity is settled (WP-0.5).** A module registers its context with `services.AddGridCoreDbContext<TContext>((builder, connection) => builder.UseNpgsql(connection, ...))` — never plain `AddDbContext`, which would give it its own connection and its own transaction. A write then wraps itself in `IUnitOfWork.ExecuteAsync(async ct => { ... })` and **never calls `SaveChanges` itself**: the unit of work attaches every registered context to one transaction, saves them all and commits. That is what makes a module write + its audit entry + its outbox row atomic.
- `Platform` exposes internals to `GridCore.Platform.UnitTests` (`InternalsVisibleTo`) for `ScheduledJobRunner.RunOnceAsync`.
- Recurring work registers with `services.AddScheduledJob<TJob>()` (scoped, resolved per run). Nothing is registered yet — the runner starts with an empty schedule.
- **The bus is live (WP-0.5).** Publish with `IEventPublisher.PublishAsync(SomeEvent.For(...), ct)` **inside** an `IUnitOfWork.ExecuteAsync` — with MassTransit's bus outbox, that writes a row to `platform.outbox_message` rather than reaching RabbitMQ, and the delivery service ships it after the commit. Publishing without then committing publishes nothing, by design.
- Consume by deriving `IdempotentConsumer<TEvent>` and registering it from the module's `AddServices` with `services.AddEventConsumer<TConsumer>()`. `ConsumerName` is the dedupe key in `platform.processed_messages` — **stable forever**; renaming one replays every event it ever handled.
- `AddGridCoreMessaging` is called **after** `AddModules` in `Web.Host/Program.cs` because it reads the consumers back off the service collection. A module registering a consumer after that line would be silently ignored.
- **MassTransit is pinned to 8.5.10 — the last Apache-2.0 line. Never bump to 9.x** (commercial licence). Dependabot (WP-0.7) must be configured to hold it.
- New events go in `src/Contracts/Events/` as positional records implementing `IIntegrationEvent`, with a static `For(...)` that stamps `Guid.CreateVersion7(occurredAt)`. The publisher rejects an event with an empty `EventId`.
- Finance's ledger is still a **no-op**: `IJournalPostingSeam` → `LoggingJournalPostingSeam` logs the balanced entry it would post. WP-2.6 replaces the implementation; the mapping (`FinancePostings`) and the balanced-or-throw guard (`JournalPostingIntent.For`) are already real.
- The MassTransit 8.x pin is now enforced twice: `Directory.Packages.props` holds it, `.github/dependabot.yml` refuses to offer 9.x, and `DependencyPolicyTests` fails the fast loop if either is edited away.
- `tests/Contracts.UnitTests` exists now and is registered in both `GridCore.slnx` and `tests/UnitTests.slnf`.
